### Recovery event naming precision

- `usdm_ingress_backpressure_recovered` (13:51:09.996638Z) means the queue
  depth fell below the low_watermark. It does **not** mean stream recovery
  completed; at that time the old generation had not yet sealed
  (seal 13:54:38.251Z, new connection 13:54:38.577Z, first-new Raw +
  Catalog COMPLETED 13:54:38.582474Z).
- The complete stream recovery boundary is: new connection + first-new
  `sequence_gap` persisted + Raw sync + Catalog COMPLETED.
- Docs must distinguish `queue_backpressure_recovered` from
  `stream_recovery_completed`.

### Precise gen5 claims

- There was no Recorder-internal silent queue drop; persisted frames passed
  CRC verification.
- Exchange-event completeness between the WebSocket close and the first new
  connection frame **cannot be proven**; the system therefore correctly wrote
  `sequence_gap`, `gap=true`, `complete=false`.

### gen6 1358.9 s saturation semantics [DERIVED]

The 1358.9 s is **not** a continuous full-queue span. The saturation timer
only resets when the queue drops to or below low_watermark (131072). The
queue hovered in 131073–262143 (writer draining ~780 fps, 7 put waits), the
30 s saturation budget expired at ~14:49:03, but `IngressBackpressureTimeout`
is raised only when a later put **encounters a full queue**; the queue became
full again at 15:11:12 and only then triggered the timeout. The current
"30 s timeout" is therefore **not a strict 30 s wall-clock recovery ceiling**.
This actual semantics is recorded as a limitation to monitor during 72h/168h.
