## Confirmed direct cause

The production exception gives the complete direct chain:

```text
websocket recv completes
  -> _receive_once timestamps the frame
  -> asyncio.Queue.put_nowait(receipt)
  -> asyncio.QueueFull
  -> IngressQueueFull("WebSocket receipt queue is full")
  -> USD-M book_ticker task terminates
  -> USD-M asyncio.TaskGroup raises ExceptionGroup
  -> MarketCollectorSupervisor raises CoreMarketTerminalFailure
  -> Recorder exits
  -> systemd starts a new PID
```

The cause was not “the default queue is 1024.” Although
`UsdMCollectorSettings.receipt_queue_capacity` defaults to 1024, the production
configuration set `ingress_queue_capacity=262144`, and runtime applies that
value to both the USD-M receipt and spool queues. Increasing that value again
would only defer the same fail-fast edge while consuming more memory.

## Producer/consumer path and execution context

The actual USD-M WebSocket path is:

```text
websockets.recv
  -> UsdMStreamCollector._receive_once
  -> bounded asyncio receipt queue
  -> UsdMStreamCollector._writer_loop (batches at most 256)
  -> envelope_from_websocket_frame
  -> StreamSpool.enqueue
  -> BoundedEventQueue
  -> StreamSpool.drain_all
  -> RawChunkWriter.append
  -> write/fsync/rotation/seal/compress/readback verification
  -> Catalog transitions
```

`recv`, receive timestamps, envelope decoding, the in-memory receipt handoff,
and the nonblocking spool enqueue occur on the asyncio event-loop thread.
`drain_all`, Raw append/write/fsync, rotation/seal/compression/readback, and the
associated Catalog work run through `asyncio.to_thread`. The M21.4 gap-event
Catalog writes also use `to_thread`. Awaiting these operations stops that
stream's Writer from consuming more receipts but does not synchronously block
the WebSocket event loop.

The receipt queue and spool queue serve different interfaces. The receipt
queue separates socket receipt/timestamping from Raw conversion and blocking
storage work. `BoundedEventQueue` is the common synchronous Raw-spool contract
used by WebSocket and REST producers. The latter is not strictly required as a
second deep buffer in this one WebSocket path: the Writer moves at most 256
items into it and immediately drains it. Production metrics confirm a spool
queue high watermark of 255, while the unobserved receipt queue reached its
262144 limit. M21.4 retains the shared spool abstraction and fixes the actual
receipt boundary rather than performing a broad storage rewrite.

At the old failure point, all items already drained by the Writer were in Raw;
items still in the receipt queue had been accepted into bounded process memory
but were not yet persisted. The frame that caused `put_nowait` to raise had
already been returned by `recv` and timestamped, but was neither enqueued nor
persisted. Further frames could have remained in the websockets high/low
buffer `(32, 8)`, kernel socket buffers, or the network. Therefore connection
closure determines the last Recorder-received/persisted boundary under the new
repair, but it cannot determine the exact exchange-event count lost outside
that boundary.

## Why the Writer fell behind

Manifest timing proves the backlog was growing before the 13:44 disconnect.
Representative `book_ticker` chunks show:

| Writer interval | Receipt span represented | records | producer rate | writer rate | lag at seal |
|---|---:|---:|---:|---:|---:|
| 13:35:42–13:36:41 | 13:31:56–13:32:35 | 13,144 | 337.9/s | 223.9/s | 246.1 s |
| 13:43:46–13:44:45 | 13:36:27–13:36:52 | 13,824 | 565.5/s | 233.5/s | 472.9 s |
| 13:48:44–13:49:46 | 13:38:58–13:39:32 | 13,807 | 404.8/s | 219.0/s | 614.6 s |

Other pre-failure chunks reached roughly 675 receipt/s while persisting about
195–261/s. The daily aggregate recorded 9,574,641 accepted, written, and Raw
records before termination; its spool gauge max was 255, not 262144. The
aggregate also contained 587,197 receive-lag observations over the 60-second
histogram ceiling. Thus the bottleneck was sustained end-to-end Raw Writer
throughput relative to `book_ticker` receipt rate, not spool-queue exhaustion.

The retained production metrics expose only aggregate write/fsync histograms;
they do not separate receipt wait, batch drain, seal/compression, and Catalog
transaction latency. This prevents assigning the deficit to one filesystem
operation. Rotations were occurring normally at about one-minute Writer
intervals. Overflow occurred inside the chunk created at 13:48:44, not on an
exact rotation boundary, so no evidence establishes a planned-rotation race.
The reconnect did not create the backlog: at 13:44 the Writer was already
persisting receipts more than seven minutes old. A reconnect burst may have
contributed, but it is not required by the evidence.

Archive work was active and successfully draining with only 1–9 backlog files
in the formal samples. Internal free space stayed healthy, and no Archive,
Catalog, kernel, or disk-space failure coincided with overflow. Concurrent
Archive/storage contention cannot be quantified from the old instrumentation,
but it is not supported as the sole cause. The Recorder consumed approximately
108% CPU in the terminal daily metrics. Formal samples show RSS increasing
from 379,846,656 to 459,087,872 bytes as the receipt backlog grew; threads
stayed at 13 and FDs stayed between 34 and 40. This is bounded-queue memory,
not evidence of a thread or FD leak.

## The approximately 12-minute tail

It was not a 1024-item drain. After the overflow, 12 newly created
`book_ticker` chunks contained 262,160 records—effectively the production
262144 receipt capacity, allowing for scheduling at the boundary. Including
the chunk active at overflow gives 13 chunks and 275,967 records. The last
old-generation chunk sealed at 14:01:02.621399, 682.684 seconds after overflow.
`CoreMarketTerminalFailure` followed 31.688 seconds later, and `SERVICE_FAILED`
followed another 22.203 seconds later while other core/side streams, snapshot
spools, metrics, and reporting completed their shutdown paths.

## Repair semantics

M21.4 introduces a finite awaitable receipt queue with these rules:

1. A short burst waits for bounded Writer space, preserving receipt order.
   The wait polls at one-second intervals to observe Writer completion and
   stop; the total saturation continuity budget is 30 seconds.
2. If the Writer fails, a waiting Producer immediately receives a stable
   `IngressWriterStopped` chained to the Writer cause.
3. At the sustained deadline, the stream closes its WebSocket with code 1013,
   stopping new production. The already-received boundary frame then receives
   a separate five-second post-close queue-handoff budget. Failure to hand that
   frame to the Writer is process-fatal `IngressPostCloseHandoffTimeout`; it is
   never dropped silently. This deadline does not bound Raw drain, fsync,
   compression, seal, or Catalog work, which must safely finish their underlying
   I/O; a permanently hung kernel I/O operation remains a known risk.
   The persisted last-old boundary frame receives the existing `sequence_gap`
   flag, conservatively making its Raw chunk incomplete even if the process
   crashes or the following Catalog evidence write fails.
4. The old generation drains and seals before a new generation opens. A
   `STREAM_DISCONTINUITY_STARTED` Catalog event records the boundary hash,
   connection/generation, queue watermark/waits, and boundary precision.
5. The first persisted event of the new generation carries the existing
   `sequence_gap` capture flag. The Writer explicitly syncs that marker before
   committing `STREAM_DISCONTINUITY_COMPLETED`; a sync failure leaves STARTED
   open and is fatal. On process restart, the stream restores the unique open
   STARTED record and its original gap/connection/generation identity; multiple
   open records are a fail-closed conflict. Its Raw manifest is therefore `gap=true` and
   `complete=false`; Normalized propagates `source_gap/source_complete`, and
   Replay's existing ERROR/INCLUDE/EXCLUDE policies see the interval. A paired
   internal event records the new connection/generation while explicitly
   keeping `historical_continuity_restored=false`.
6. `book_ticker` and `agg_trade` can reconnect at stream scope after this
   durable boundary; they have no Snapshot recovery and never claim the old
   interval complete. Healthy core streams and the other market remain alive.
7. `diff_depth` does not use stream-only recovery. It marks readiness failed,
   requests market-local resync, retires the whole USD-M capture session,
   discards the old bootstrap state, opens fresh connections, obtains a new
   public Snapshot, and becomes READY only after correct USD-M `U/u/pu`
   bridging. The Raw `sequence_gap` remains incomplete after readiness returns.
8. Mark-price and liquidation WebSockets use the same bounded USD-M primitive;
   their supervising side-data tasks remain isolated from core termination.
9. Raw append, drain, fsync, seal, Catalog, or early Writer failure remains
   fail-closed. A failed active writer descriptor is closed without sealing;
   its partial remains for normal startup recovery.

Stop can interrupt queue wait and reconnect backoff. Every in-flight mutating
Raw or gap-Catalog thread call has an asyncio Task owner which is shielded and
awaited through cancellation before abort or close may proceed. Python cannot
safely cancel an OS write, fsync, compression, or SQLite call already running
in a worker thread; a permanently hung call therefore also keeps its owner
waiting.

## Observability

Transition-only structured logs now include stream, connection ID, generation,
outcome, receipt capacity/depth/high watermark, aggregate queue-wait count and
p50/p95/p99 bounds, last batch size, last/max drain, and last/max append,
write, fsync, and seal duration. They contain no Raw payload, proxy URL, or
credential and do not emit per-message records. Existing metric and soak
schemas remain unchanged.

The deterministic offline benchmark covers baseline, post-reconnect burst,
slow append, slow fsync, slow seal, batch capacities 8/64/256, and a near-full
queue. With 15,000 total synthetic events across the matrix, all scenarios had
zero loss, zero duplicates, correct order, and high watermarks no greater than
capacity. The detailed rates, latency percentiles, RSS, FD, and thread maxima
are in `metrics/offline-ingress-benchmark.json` in the evidence archive.

## Contract and compatibility decision

No Raw payload format, Raw Manifest schema, Catalog schema, Normalized schema,
Replay API, public consumer contract, production configuration, dependency, or
soak schema changed. The repair uses the existing `capture_flags.sequence_gap`
and Manifest `gap/complete` semantics from ADR-0010, plus additive internal
Catalog event types. Older Raw remains readable. New incomplete chunks are
handled by existing Normalized and Replay policies.

## Same-class risks and exclusions

Code search covered `IngressQueueFull`, `QueueFull`, `put_nowait`, both queue
capacities, `TaskGroup`, Writer tasks, `drain_all`, and `close_and_seal`.

- All three USD-M core streams and both USD-M side WebSockets used the shared
  failing receipt primitive and receive this repair.
- Spot core WebSockets have an analogous `put_nowait` receipt overflow path.
  It remains process-fatal and is not silently changed in a USD-M-specific PR;
  Spot regression tests pass, and a separately reviewed parity repair is
  required.
- Spot side REST/exchange-info and USD-M REST side data use synchronous bounded
  spools with immediate drain/cursor rules, not this receipt queue.
- Ordinary non-depth WebSocket disconnects remain distinguished by immutable
  connection IDs but are not automatically converted into `sequence_gap` in
  this patch. This broader continuity-policy change requires separate review.
  **M21.4.11 implements that review outcome**: every reconnect boundary
  (unexpected disconnect, planned rotation, server shutdown, session
  restart) now carries persistent gap evidence in both markets; see
  `docs/milestone_evidence/M21.4-72h-failure-and-reconnect-integrity.md`.
- A permanently hung kernel filesystem operation cannot be made promptly
  cancellable by asyncio. M21.4 bounds queues and network receipt but retains
  fail-closed process supervision for storage integrity failures.
