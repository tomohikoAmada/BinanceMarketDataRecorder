## Root cause and unintended relaunch record

At `06:50:59 UTC`, `apt-daily-upgrade.service` began an unattended upgrade.
It upgraded glibc packages from `06:51:10` and Python 3.12 packages from
`06:51:59`. At `06:51:11`, systemd recorded `Reexecuting requested` from a
`systemctl` client owned by `apt-daily-upgrade.service`. The resulting service
restart wave stopped the original observer at `06:51:20.087964` and Recorder
at `06:51:20.090640`, along with network, SSH, journald, cron, chrony, and
other system services. The kernel boot ID did not change, but Recorder PID,
systemd InvocationID, and service instance did.

Because the transient unit survived the manager reexecution definition, the
host maintenance path relaunched its original new-stage command twice despite
the unit's `Restart=no` property. The first relaunch was interrupted while
freezing manifest membership. The second published the preserved, ineligible
root `2h-bf19cceb37504599873d84b7a3f13b57` with stage-start SHA-256
`9c9f4102337b12f68133fe2ea7f8a2f90c70582dcd837809ea9b811d702d97c8`.
It reported `REVIEW_REQUIRED`, one `readiness_not_ready` blocker, and service
instance `16a8421b-5011-4c06-9b37-fe5b48fe3f7e`. It is an unintended
host-maintenance relaunch artifact, not an authorized second Formal attempt,
and receives zero credit.
