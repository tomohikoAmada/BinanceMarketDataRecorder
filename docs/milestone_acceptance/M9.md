## Architecture decisions

ADR-0014 selects direct Disk Arbitration callbacks via PyObjC rather than a
mount-directory polling substitute. Only objects explicitly described as
non-internal and UUID-bearing can be registration candidates. UUID plus marker,
storage ID and relative path are identity; name and mountpoint are observations.
Readiness is capability-based and writes only inside an explicitly selected or
already-registered folder. External storage remains outside every Collector
failure dependency.

M9 exposes no mount, unmount, eject, formatting, repair, archive copy, manifest,
local-delete, forecast, GUI, account, credential, trading, or M10 behavior.

## Known limitations

M9 provides the lifecycle listener library but does not install a persistent
monitor; supervised service/launchd assembly is M14. `storage status` performs a
fresh readiness probe in each registered writable directory. Physical
filesystem durability and removal behavior still require the M17 matrix.
`LOW_SPACE`, archive copy/verify, safe deletion, forecast, and eject state
behavior remain M10-M12.

## Data compatibility and rollback

M9 does not change EventEnvelope, Raw chunk bytes, manifests, stream schemas,
order books, side-data records, operational aggregates, or replay ordering. It
additively adds `storage_targets`, the registered-storage marker contract,
storage state JSON, and a macOS-only runtime bridge. The M8 daily external-space
sentinel changes from milestone-pending language to
`NO_REGISTERED_TARGET_SAMPLE`; no numeric value is fabricated.

Rollback disables storage commands and reverts M9 while leaving inert Catalog
rows and marker/archive data untouched. It never deletes user data or changes a
filesystem. Internal Raw capture remains independent.
