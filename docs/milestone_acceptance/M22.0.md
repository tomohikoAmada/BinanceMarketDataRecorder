# M22.0 Acceptance — VPS / remote archive implementation decomposition freeze

## Result

M22.0 is **ACCEPTED** as a documentation-only milestone. No production code,
remote archive code, deployment code, or tests were implemented or changed.
M22.1 is **NOT STARTED**.

The approved D0/D1 architecture in ADR-0028, ADR-0029, and ADR-0030 was not
reopened. This record freezes the implementation sequence in
`docs/milestone_plan.md` and makes the following accepted review corrections
authoritative:

- M22.3 requires final published-artifact namespace durability, durable
  Archive Set/physical-media metadata, durable receipt and receipt-namespace
  metadata, and fail-closed behavior when the selected platform cannot prove
  those commits. A pre-rename file fsync is not sufficient.
- Existing same-host `ArchiveState` and `archive_transactions` retain their
  ADR-0015 meaning. Remote transfer leaves a VPS source `SEALED`.
- Remote lifecycle semantics are separately frozen as
  `SEALED -> REMOTE_DELETE_PENDING -> REMOTE_DELETED`; pending is not
  completion, and terminal deletion follows exact unlink and filesystem
  durability.
- M22.4 is split into non-destructive M22.4A and destructive M22.4B. Remote
  persistence is a separate projection and is not added to
  `ARCHIVE_CHUNK_STATES`.
- M22.7 is split into named VPS capacity profile M22.7A and systemd/readiness/
  exact-artifact profile M22.7B. Generic ADR-0016 threshold behavior remains
  unchanged until M22.7A.

## Compatibility and validation freezes

Pre-M22 Catalog -> M22 binary is **SUPPORTED** through additive persistence
and unchanged existing-table meaning. M22 Catalogs after remote states have
been written -> pre-M22 binary is **NOT CLAIMED / NOT GENERALLY SUPPORTED**;
old binaries do not know the new remote states, and remote states must not be
hidden by relabeling them as `LOCAL_DELETED`. A deployment/rollback policy is
required before production remote states are enabled.

M22 intermediate artifacts are development/CI/Mac/LAN artifacts and are not
Production Ready. The merged PR #11 reconnect correction remains not deployed;
the historical `f659895…` 72-hour result remains historical and is ineligible
for 168 hours. The final integrated M22 artifact must independently run:

```text
exact artifact identity -> readiness -> 2h -> 12h -> 24h -> 72h -> 168h
```

No M21 evidence transfers and no stage starts automatically. Historical M21
documents were not rewritten.

## Observations

- **OBS-01:** The prior plan ended with the approved D0/D1 architecture freeze
  followed by Future Work; it had no M22 implementation sequence or M22
  acceptance record.
- **OBS-02:** `ChunkState` currently maps same-host archival through
  `SEALED -> ARCHIVE_COPYING -> ARCHIVE_VERIFYING -> ARCHIVED_VERIFIED ->
  LOCAL_DELETE_PENDING -> LOCAL_DELETED`; `ArchiveState` is
  `COPYING -> VERIFYING -> VERIFIED -> LOCAL_DELETE_PENDING ->
  LOCAL_DELETED`.
- **OBS-03:** `archive_transactions.chunk_id` is unique, and its Catalog
  reservation atomically requires `SEALED`, inserts the same-host transaction,
  and changes the chunk to `ARCHIVE_COPYING`.
- **OBS-04:** Recovery derives the archive mapping from
  `ARCHIVE_CHUNK_STATES` and requires a matching `archive_transactions` row;
  unknown remote states cannot safely be inserted into that path.
- **OBS-05:** Generic forecast behavior uses ADR-0016 percentage thresholds
  (40% warning, 15% critical, 5%/10 GiB emergency) and the generic hard-reserve
  formula; the named VPS 18/14/12/10 GiB policy is not yet implemented.
- **OBS-06:** D0/D1 contracts require local verification and durable receipt,
  durable VPS pre-delete authorization, immediate source revalidation,
  deletion durability, separate terminal state, CASE A/B/C/D recovery, and
  post-session SQLite-supported snapshots. They explicitly leave these future
  implementation concerns.
- **OBS-07:** No current `docs/milestone_acceptance/M22.0.md` existed before
  this milestone.
