## SQLite source and post-session binding

`Catalog.open_live_read_only()` is the explicit live backup source. It uses
SQLite URI `mode=ro`, `query_only=ON`, `busy_timeout=30000`, foreign keys, and
normal SQLite locking, and never appends `immutable=1`, even when no WAL
sidecar exists at open. Existing `Catalog(path, read_only=True)` static-observer
behavior is unchanged. The narrow `Catalog.backup_to()` calls
`sqlite3.Connection.backup()`; it does not copy the main database, WAL, or SHM,
checkpoint the source, add schema, or mutate live state.

`PostSessionArchiveWorkflow` invokes the unchanged
`RemoteArchiveSession.run_one()` exactly once. No-work returns without a
snapshot. A successful pending or deleted session freezes its exact receipt ID
and authority as the snapshot lower bound. Pending permits only pending or its
validated monotonic deleted successor; deleted permits only deleted. Both
remote self-validation and local validation open the snapshot database itself,
require the exact one-row `PRAGMA integrity_check` result `ok`, and call the
existing `Catalog.remote_archive_transaction(receipt_id)`. That authoritative
reader reparses receipt bytes and validates chunk/source binding plus the exact
initial and lifecycle-dependent terminal events.

`PostSessionSnapshotError` reports code `POST_SESSION_SNAPSHOT_FAILED`, the
exact triggering receipt, the committed pending/deleted state, the original
session result, and the underlying cause. It states that the archive session is
already committed. The explicit `snapshot_post_session()` library retry takes
only the existing receipt/state and snapshot transport; it never selects a
source, receives Raw, creates a receipt, authorizes, deletes, or advances to a
next source.

## Remote generation and transport

`CatalogSnapshotExporter` owns
`state/catalog-snapshot-staging/<canonical-uuid4>/`. Each invocation directory
is mode 0700 and contains a strict generated ownership marker, a mode-0600
kernel `flock` lock, and one mode-0600 `catalog.sqlite`. A fresh destination
connection receives SQLite Online Backup and closes before validation. Only the
standalone database is streamed; no sidecar or predeclared remote hash exists.
Cleanup accepts only a direct canonical UUID4 child with the exact marker and
an acquirable inactive lock. Active, malformed, unknown, symlinked, or unrelated
entries are preserved/fail closed, and the live Catalog/Raw/manifests/state
siblings cannot be cleanup targets.

`RemoteTransport.open_catalog_snapshot(receipt_id, required_state)` is the only
new transport method. In-process uses the real exporter. OpenSSH adds only the
fixed hidden command `_remote catalog-snapshot <lowercase-sha256>
<REMOTE_DELETE_PENDING|REMOTE_DELETED>`, retains `shell=False`, BatchMode,
normal host-key checking, inherited stderr, and no arbitrary path/command or
credentials. Generation, self-validation, and streaming are one command.
The generalized process-backed stream makes successful EOF conditional on child
exit zero and retains bounded terminate/kill/reap behavior. Complete valid
SQLite bytes followed by nonzero exit are rejected before publication.

## Local validation, manifest, and retention

An explicit Offline Workspace root contains `catalog-backups/`. The receiver
streams in 1 MiB blocks to unique `.staging/<snapshot_id>/catalog.sqlite`,
fsyncs and closes it, fsyncs its directory, then reopens the full file to derive
`stored_bytes` and SHA-256. It independently performs standalone SQLite,
integrity, Catalog structure, exact target receipt/state/event, and lower-bound
validation against those transferred bytes.

The exact `catalog-snapshot-manifest.v1` fields are `schema`, `snapshot_id`,
`receipt_id`, `chunk_id`, `required_remote_state`, `observed_remote_state`,
`stored_bytes`, `sha256`, `verification_version`, and `verified_at_utc_ns`.
Canonical JSON plus LF is written mode 0600, fsynced, reopened, strictly parsed,
and generation-directory-fsynced before the UUID4 directory is published and
the `snapshots/` parent is fsynced. UUID4 is generation identity; SHA-256 is
content identity, so equal content remains distinct history.

Mirrored `retention-0.json` and `retention-1.json` use exact canonical
`catalog-snapshot-retention.v1` fields `schema`, `generation`, `latest`, and
`previous`. References contain only `snapshot_id` and `manifest_sha256` and are
valid only when their generation, strict manifest, snapshot size, and snapshot
hash validate. The higher valid generation wins; equal generations must have
byte-identical documents; one valid slot recovers. A durable initialization
marker distinguishes true first use from initialized loss/corruption, so both
invalid slots fail closed rather than using mtime or scanning for a newest
snapshot.

Each update writes/fsyncs/replaces/fsyncs the older or invalid slot first, then
the other slot with identical bytes, and rereads authority. G1 produces
latest=G1/previous=null; G2 produces G2/G1; G3 produces G3/G2. Only after both
slots are durable may exactly owned, validated, unreferenced older generations
be removed. Cleanup failure is nonfatal and unknown files are not swept.
