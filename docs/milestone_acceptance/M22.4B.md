# M22.4B Acceptance — Remote source deletion / durability / kill recovery

## Result

M22.4B is **IMPLEMENTED** on the dedicated feature branch based exactly on
`22521e32c7efe0b89ef61fa2e05e9027a4fe7c00` (tree
`75eaf22c191de0420a82332dd14c3518c768096b`). This is the first destructive
remote milestone. It does not claim merge, deployment, production readiness,
SSH/`RemoteTransport`, or the M22.6 Catalog snapshot.

The destructive call key is only the lowercase SHA-256 `receipt_id`. The
caller cannot supply a source path, receipt bytes, Archive Set medium, or local
archive object and therefore cannot rebind durable VPS authority. The executor
reparses the exact persisted receipt bytes, recomputes its identity, validates
the initial event and lifecycle-specific event set, requires physical
`chunks.state == SEALED`, excludes same-host ownership, reads the exact retained
manifest, reconstructs the complete M22.1 descriptor, and binds the descriptor
digest to both row and receipt.

## Exact deletion and durability boundary

M22.4B deletes exactly one object: the authorized sealed Raw direct child of
`layout.sealed`. It never deletes the `raw-chunk-manifest.v1`, chunk row,
receipt bytes, remote transaction, initial event, or terminal event. No glob,
recursive deletion, generic cleanup API, shell command, or arbitrary caller
path exists.

On supported Linux/macOS capability profiles, CASE A:

1. validates exact pending authority and the retained manifest/descriptor;
2. anchors the exact `sealed/` directory with `O_RDONLY`, `O_CLOEXEC`,
   `O_DIRECTORY`, and `O_NOFOLLOW` and verifies its identity;
3. opens the exact Raw leaf relative to that parent with `O_RDONLY`,
   `O_CLOEXEC`, and `O_NOFOLLOW`, verifies a regular file, and keeps the Raw fd
   open across namespace mutation;
4. freshly streams the complete stored bytes through that fd and verifies size
   and SHA-256, then resets/duplicates the held descriptor explicitly and
   verifies complete decompressed byte count and SHA-256;
5. rechecks the exact pending/SEALED/no-same-host Catalog authority and compares
   `st_dev`, `st_ino`, `st_size`, and `st_mtime_ns` between held fd and final
   parent-relative no-follow leaf stat;
6. performs the only new production destructive primitive,
   `os.unlink(exact_leaf, dir_fd=parent_fd)`;
7. proves absence, fsyncs that same anchored parent descriptor, and proves
   post-fsync absence; and
8. only afterward atomically commits `REMOTE_DELETED` and one canonical
   terminal event, then reads back the row/event, exact retained manifest, and
   source absence.

The platform preflight requires no-follow flags, directory-fd opening,
parent-relative open/stat/unlink, no-follow stat, and directory fsync. It
performs a non-destructive fsync capability probe before CASE-A unlink. A
failure or unsupported platform retains `REMOTE_DELETE_PENDING` and the Raw.
Windows is unsupported. macOS is development/CI support only when the same
POSIX primitives succeed; Ubuntu 24.04 x86_64 remains the future production
target and is not deployed by this milestone.

## Terminal authority and recovery

`Catalog.commit_remote_deleted()` operates only on one existing exact pending
row. Inside one `BEGIN IMMEDIATE` it repeats receipt/initial-event/source/
SEALED/no-same-host/no-terminal validation, updates only state and terminal
timestamps, and inserts one `remote-deleted:<receipt_id>` event. The row and
event share the terminal reconciliation timestamp and commit atomically. Its
canonical evidence contains exactly chunk/receipt identity, source absence,
descriptor and manifest digests, parent-fsync evidence, source path, stored
byte count, and stored digest.

Authoritative remote-row reads now require exactly one valid initial event for
pending state and exactly that initial event plus one valid terminal event for
deleted state. Pending-plus-terminal, deleted-without-terminal, wrong receipt,
wrong transition, timestamp/evidence/key corruption, duplicates, and extra
events fail closed. Exact terminal retry performs no write and does not change
timestamps or event count. An ambiguous SQLite commit result is inspected
through a fresh Catalog connection: only exact pending/no-terminal or exact
deleted/terminal outcomes are accepted.

CASE B uses the same authority and retained descriptor but begins by proving
the Raw leaf is absent. It performs no unlink, rechecks pending authority,
fsyncs the anchored parent, rechecks absence and authority, and terminalizes.
Raw reappearance before terminal commit fails closed. Startup integrates only
this recovery-only entry; CASE A remains preserve/report and requires an
explicit deletion call. CASE C, CASE D, terminal-present, and impossible
same-host/remote overlap never mutate the filesystem or terminal state.

Deterministic fault points cover K0 through K5. Spawned-process SIGKILL tests
kill fresh children at K1 (validated/present), K2 (unlinked/not fsynced), K3
(parent durable/not terminal), K4 (uncommitted row/event transaction), and K5
(terminal committed). Every recovery opens fresh `StorageLayout`, `Catalog`,
and `RemoteDeleter` objects. A two-process same-receipt test forces both callers
through final destructive validation, permits no alternate path, and converges
to one terminal event. The real post-unlink production `os.fsync(parent_fd)` is
faulted only after K2 arms the injection; at failure the Raw is directly proven
absent while the row remains pending and the terminal event is absent.

## Non-scope and rollback

M22.5 and M22.6 remain **NOT STARTED**. There is no SSH, `RemoteTransport`,
network protocol, generic delete API, manifest cleanup, bulk deletion, or
Catalog snapshot implementation. Rollback stops new explicit CASE-A attempts,
preserves all retained manifests/receipts/Catalog evidence, and reconciles only
already-absent sources through exact durable pending authority.
