## Scope and compatibility

M21.0 prepares bounded archive automation and trustworthy sampling evidence for
later M21 long-run acceptance. It does not begin a soak:

1. bounded, re-entrant Archive Drain with a dedicated cross-process DrainLock;
2. archive and soak systemd companion service/timer management;
3. `m21-soak-sample.v2` JSONL observations with an explicit `storage_id`;
4. SQLite-only archive backlog aggregation from one consistent read snapshot.

There is no Raw, Raw manifest, Catalog schema, normalized schema, or replay API
change. Soak schema v2 explicitly separates:

- systemd active/sub state and authoritative Linux `MainPID`;
- observed service-state PID, PID mismatch, heartbeat age/freshness/error, and
  derived application status;
- current market/runtime health from last-observed state-file evidence.

A stale heartbeat, inactive/failed systemd unit, missing systemctl evidence, or
PID mismatch cannot report Spot or USD-M as currently READY. `/proc` sampling
uses systemd `MainPID`; state-file runtime metrics are current only when the
heartbeat is fresh and the two PIDs match.

Archive backlog is:

```text
global unassigned SEALED queue + selected storage_id inflight transactions
```

The component file/byte counts and sums execute in SQLite. Historical
`LOCAL_DELETED` rows are not loaded as Chunk objects and are not backlog.

## Certified Catalog concurrency boundary

The integration proof starts with 50 real SEALED Chunks, then concurrently runs
one independent Recorder writer that creates and seals 200 more Chunks and one
independent Archive Drain writer against a real WAL Catalog and a real temporary
archive directory. The single run processed 250 files and completed 250 archive
transactions; external verification, unique transaction ownership, legal
incomplete states, process exit codes, and `PRAGMA integrity_check=ok` passed.

The certified boundary is exactly:

- one Recorder write process;
- one Archive write process;
- SQLite WAL, 30-second busy timeout, and `BEGIN IMMEDIATE` serialize writes;
- DrainLock prevents multiple Archive Drain processes.

This is not a claim of arbitrary multi-writer support.
