## Explicit profile and dependency identity

`RecorderConfig.capacity_profile` accepts only omitted/`None` or the literal
`vps-production-v1`. Only `[recorder].capacity_profile` in the explicitly
loaded TOML selects the VPS profile. Unknown literals fail validation. Host,
platform, architecture, systemd, path, capacity, proxy, environment, and all
other config fields have no selection authority; there is no
`--capacity-profile` or profile environment variable.

Generic/local configuration retains existing Recorder environment behavior.
When the TOML explicitly selects the VPS profile, all
`BINANCE_MARKET_RECORDER_*` settings are rejected and proxy mode must be
`direct`. The certified unit contains no operational Recorder variable,
environment file, or pass-through environment authority; it explicitly empties
all upper- and lowercase standard proxy variables. Effective unit verification
and live process-environment verification independently reject routing drift.

`requirements/linux-x86_64-python312.lock` was generated with pip-tools 7.5.1
under Linux amd64/Python 3.12.13 using `--generate-hashes --strip-extras`, and
has SHA-256 `44cd373324f2af5f2682851996bc59a16199c65f8de9e98089131e1c67d6f335`.
The CI Ubuntu 24.04 job installs it with `--require-hashes` before the existing
CI/dev lock. A separate clean Ubuntu production venv installs only the exact

The verifier parses the retained hash lock into normalized Python packaging

## Recovery, capacity, and lifecycle

The VPS runtime refuses to start without a validated runtime identity. It
publishes STARTING evidence, opens the Catalog, completes existing recovery,
takes an immediate actual internal-filesystem observation, and only then may
construct collectors. A periodic observation continues while running.

Actual free bytes <=10 GiB at startup prevents Collector construction. At
runtime it requests the ordinary graceful Collector stop and awaits completion,
which retains each Collector's drain/seal contract. Both paths record one
`DISK_EMERGENCY_STOP`, explicitly state that no unarchived Raw was deleted, and
open durable `session_restart` discontinuity evidence for every Spot/USD-M core
stream not already carrying an open gap. The termination reason is
`HARD_RESERVE_SAFETY_STOP`; normal return makes process exit zero, so the frozen
`Restart=on-failure` policy does not loop. A core runtime failure still raises,
publishes FAILED evidence, and exits nonzero/restart-eligible. ETA-derived
EMERGENCY above the actual reserve never stops collectors.

A later observation sees space consumed or released by co-resident processes
without cause attribution. Release after a clean hard-reserve stop never starts
the service; the operator must explicitly start it and rerun all startup gates.

## Readiness and rollback

`deployment readiness` has an external 300-second deadline and no HTTP server
or runtime watchdog. READY requires the expected active unit, MainPID equal to
the live fresh service-state PID, exact runtime/file/effective identity, selected
profile, open read-only-valid Catalog, completed recovery, existing full Spot
and USD-M core readiness, and a current valid profile capacity observation with
actual free bytes above 10 GiB. WARNING/CRITICAL/EMERGENCY above 10 GiB and an
insufficient ETA history with a current safe observation may remain READY.
Startup and intentional stopped states are NOT_READY; invalid/missing identity,
failed recovery/service, stale/dead claimed running state, invalid/unavailable
capacity, or deadline expiry are FAILED.

Stopped deploy/upgrade procedures preserve exact old and new bundles and never
mutate a running venv. Rollback compatibility reads current Catalog remote
transactions and fails closed unless the exact preserved M22 target declares
every durable state. A pre-M22 identity cannot pass. Rollback never changes
Raw, Catalog, receipts, lifecycle state, or data. No new remote-delete authority
was added.
