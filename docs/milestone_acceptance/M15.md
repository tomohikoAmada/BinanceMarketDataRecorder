## Architecture decisions

Raw remains the immutable system of record. Normalized data is a separate
content-addressed derived plane selected through a specific build manifest;
glob-reading every artifact across builds is forbidden because builds may
share or supersede partitions. Identity is based on content and versions, not
filesystem enumeration or archive mountpoints.

The Collector/service path does not invoke Parquet work. The normalizer uses
internal disposable `.work` files, bounded 10,000-row sort/write batches and
at most 32 open partition spools. Logical identity is the compatibility
promise; a writer/profile change requires a new version even if it can produce
different physical bytes for the same logical rows.

## Known limitations

Each run selects every known Raw manifest rather than offering an incremental
time-range selector. Content addressing reuses identical artifacts, but a
larger source set may create new hour partitions because duplicate-source
lineage changes. There is deliberately no mutable “latest build” pointer;
consumers must select a build manifest, with generic discovery/replay reserved
for M16.

Memory is bounded by fixed sort/write batches except for all candidates sharing
one semantic identity. That collision group should normally be small but can
grow under pathological duplicated input; R-032 retains live-scale validation.
Temporary sort/spool disk can approach the logical input size before Parquet
commit, so M11 may suspend this non-core operation under pressure. M15 does
not make normalized data a second Raw backup.

Complex repeated structures remain canonical JSON columns. This is lossless
and language-neutral but less directly typed than scalar fields. Logical
determinism is tested and versioned; physical Parquet byte identity is bound to
the exact `bmdr-parquet.v1` writer profile and dependency.

## Data compatibility and rollback

M15 does not change EventEnvelope v1, Raw chunk framing, exact payload bytes,
Raw manifests, Catalog chunk/archive state, external archive artifacts, M6
checkpoint bytes, Collector behavior or service lifecycle. It adds derived
`normalized-dataset.v1` artifacts/manifests and two additive metric counter
names. Existing Raw readers remain compatible.

Rollback stops normalization and deletes only artifacts below the versioned
normalized dataset root whose manifests prove M15 ownership, then reverts the
M15 code and dependencies. Preserve all Raw, Raw manifests, Catalog/archive
evidence, checkpoints and operational metrics. Rebuild a different normalized
version from the same verified Raw; never edit or delete Raw as rollback.
