## Delivered scope

- Strict executable `EventEnvelope v1` with exact payload bytes, receive clocks,
  exchange times, Binance market/stream identity, connection/collector
  provenance, lossless sequence mapping, encoding, and capture flags.
- ADR-0010 byte-freezes Raw chunk v1: fixed big-endian header, canonical CBOR,
  length-prefixed frames, bounded allocation, Castagnoli CRC32C, exact checksum
  coverage, file names, Zstandard profile, fsync order, recovery and seal states.
- Single-owner append writer with complete-write loop, configurable 60-second /
  128-MiB first-hit rotation, configurable maximum one-second durability window,
  idle-stream sync hook, and 16-MiB default frame limit.
- Explicit bounded ingress queue. Capacity exhaustion raises
  `IngressQueueFull`; no event is silently discarded.
- Forward scanner that retains only one bounded frame plus aggregate metadata,
  truncates only incomplete EOF tails, and quarantines header, flags, length,
  checksum, CBOR, schema, or chunk-identity corruption.
- Verified sealing to a separate Zstandard artifact, full decompressed readback
  SHA-256, canonical atomic manifest, Catalog transaction, and source deletion
  only after Catalog commit.
- SQLite Catalog with FULL synchronous/WAL lifecycle metadata and idempotent
  transitions. It stores no event payload corpus.
- Startup partial recovery and sealed manifest/artifact reconciliation after
  crash boundaries.
- Python and standard-library Go golden-vector verification.

## Excluded scope and known limitations

M3 contains no Binance network parsing, REST call, WebSocket connection,
production Collector, order-book reconstruction, normalization/Parquet,
external archive, GUI, account/credential, strategy, backtest, or trading code.
Only synthetic envelopes are written.

The writer is deliberately single-owner. A future Collector must poll the spool
loop often enough to invoke idle durability/rotation checks and must convert
queue saturation into an explicit collector fault/gap. M3 does not benchmark
real Binance payload rates or live disk growth. Sealing temporarily needs both
uncompressed and compressed artifacts; M11 must include this overhead.

Catalog/filesystem operations cannot be one atomic transaction. Recovery
reconciles defined boundaries, retains the uncompressed source before Catalog
commit, and never treats a mismatched existing target as success.

## Compatibility and rollback

M3 establishes the first executable Raw compatibility boundary:
`event-envelope.v1`, `raw-chunk.v1`, `raw-chunk-manifest.v1`, and
`zstd-frame.v1`. No production market data exists, so rollback can revert the
single M3 commit and delete only test artifacts. Once any non-test Raw v1 data
exists, this reader must remain available and sealed chunks may not be rewritten.
