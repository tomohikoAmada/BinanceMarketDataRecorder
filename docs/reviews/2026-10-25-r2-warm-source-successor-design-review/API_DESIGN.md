# Minimal successor interface and control flow — design only

The preferred implementation is one read-only private completion helper plus small orchestration changes in the private controller. It imports the exact installed20e57 `VpsReadinessEvaluator` and existing source identity/systemd APIs; it must not copy/rewrite the evaluator predicates. No source edit, daemon, production tuning, second Catalog scan or installed RECORD/dependency rescan is proposed. This document is not executable successor code.

## Three narrow operations

1. **Retain the first full attestation.** At first current strict PASS, run the one unchanged canonical `deployment readiness` command, with timeout no greater than min330s/positive remainder of the original1200s deadline. Preserve its exact bytes/exit/parse/timeout result and before/after clocks and bindings. READY implies the default source identity/catalog validators passed under frozen source control flow; it is an earlier full attestation, not T0 freshness. Fail without a T0 if absent, malformed, mismatched, late or not durable.
2. **Evaluate current completion.** A bounded read-only canonical-Python child receives phase=end|start, expected scope/incarnation, the full-attestation receipt path+SHA, strict raw state path+SHA and the unchanged original warm deadline. It loads current canonical config/identity, checks their bytes/paths/permissions, constructs the real source SystemdManager with exactly the CLI factory's data_root/config_file/user/group/sys.executable/profile arguments, and calls exact `VpsReadinessEvaluator.evaluate()` once per bounded snapshot-pair attempt. Its two injected callbacks are guarded static attestation adapters described below. Do not call `wait_for_readiness` or the CLI again. Keep the real default environment/process-alive/state/UTC providers.
3. **Commit completion evidence.** The child only emits result/evidence; it cannot restore, start, stop, mask, write scope files or enter the controller's generic failure-restoration dispatcher. Root controller preserves original stdout/stderr/partial output/timeout bytes, publishes the phase receipt durably, validates the protocol/bindings/deadline/freshness and only then considers the endpoint/T0. Existing parent failure handling remains the single control owner.

The child is a separately frozen, guarded-entry read-only script, not another mode in the current controller dispatcher, whose generic error handling can restore services. Use installed canonical Python with `-B` and the same bmdr principal as the unchanged canonical CLI. Its module origins and decision-module SHA must match the frozen wheel/source maps. No workspace import fallback or monkeypatch of source globals is permitted.

## Exact source reuse

Construct VpsReadinessEvaluator with actual configured ProductKey set, current canonical data_root/DeploymentIdentity and real SystemdManager. Only supply `identity_verifier` and `catalog_ready` adapters. Do not cache/fake the manager, process environment, process_alive, service-state read or real UTC clock. Source `verify_install_contract`, `verify_effective_properties`, `runtime_properties`, actual Recorder `/proc` environment, heartbeat/status/identity/profile/recovery/topology/products/capacity checks all run afresh. See PREDICATE_MAP.json for all28 predicate groups.

The identity adapter calls real source `verify_identity_files` with `verify_installed=False`, expected canonical config/profile and require_root_controlled=True. This still rehashes retained wheel/lock/config/unit/sidecars. It runs current source `verify_vps_identity_permissions` and `verify_vps_control_chain`, using only the earlier verified installed_artifact path mapping for the latter. Package/dependency content proofs remain earlier static evidence; current fields that were not rescanned must stay None or explicitly reused under a separate provenance field, never be copied into a falsely fresh full evidence map.

The catalog adapter returns a boolean only after an explicit valid bound attestation and current canonical same-file guard. It is not `lambda path: True`. It records that integrity was proved during the first full command and is reused, along with its original receipt SHA and times. Missing, expired, wrong-scope/boot/incarnation/identity/path/file proof or a failed guard returns False/raises a source-recognized failure; it never falls back to True or reruns a hidden heavy scan.

## Completion receipt is not stock full deployment readiness

Top-level kind must explicitly mean `warm completion using bounded static attestation and fresh source dynamic evaluation`. Include the unmodified nested source public_dict, both callback-use records, the earlier full receipt reference, before/after guards and strict raw witness. It is legitimate to require the nested source stateREADY under those declared callbacks. It is not legitimate to publish it as a fresh stock `deployment.readiness` command or a fresh Catalog/installed-package audit. Preserve the earlier full result separately in warmup-result, with its earlier scope/time label. Bind phase receipt SHA into warm end/start/owner-start controls so final independent review sees the distinction.

## Original timing and observation contract

One original warm begin establishes1200s once; publish UTC/BOOTTIME/monotonic begin and fixed deadline in a small warm-budget receipt before work that can fail. Preserve actual enable-request timing when available; never reconstruct it from a later row. All new end/start completion checks and the final decision to create T0 must remain inside that same original deadline—no new grace window. This is an explicit conservative pre-T0 check; if existing prestart admission consumes the remaining budget, fail honestly rather than extending1200. Reserve the remaining portion of that original warm budget in the existing prestart admission call instead of claiming zero remaining work; do not enlarge total warm allowance or change own86400/min+60/audit/restoration budgets.

Each read-only completion child is capped by min30s/the positive remaining original warm time. Before/after parent checks reject a late result even if READY. No performance promise is made; actual Linux qualification must measure this bounded path. If30s cannot be justified in that environment, it must fail or receive a separately reviewed smaller/explicit bound, never an implicit extension.

Do not blindly sleep another30s after the blocking early CLI. The minimum change is an endpoint-aware sleep cap: once the original minimum12 actual warm observations is already met, shorten only the last wait to the still-unreached first-strict+300s endpoint (and always to the remaining1200s deadline). Otherwise retain ordinary30s sampling. Require a newly acquired strict observation at/after the endpoint, never reuse the pre-CLI first row as the end. Do not fabricate skipped rows or count completion/race probes toward minimum12 or the formal2880 denominator. This prevents ordinary post-CLI cadence rounding from wasting the observed narrow remaining budget while preserving>=300s and actual samples.

For a strict/source publication race, retain both witnesses and permit at most three fresh pair attempts inside the same min30s/global deadline. Each source evaluator reads real current state. Require its evidence.service_state to deep-equal the decoded strict raw witness for the accepted pair, with before/after expected invocation/PID/NRestarts0/boot/config/identity/service-instance. Completion probes are tagged separately and do not dilute warm/formal denominators. Only publication advancement is retryable in this pairing layer; source FAILED or true resource/write/config/env/trust failures are not turned into success or hidden retries. Original normal BLOCK warm-loop recovery remains unchanged.

Immediately before owner-start, ensure the accepted source/strict timestamps still satisfy the source and strict freshness horizons at the decision clock, and same-incarnation/window guards still hold. If evidence durability or elapsed time invalidated the pair, no T0; obtain a new allowed pair within the fixed remaining budget or fail. This is bounded snapshot evidence, not atomic or continuous READY across all time.

## New metadata controls and qualification gate

Future reader/export must include warm-budget, full warm-readiness-check and end/start completion receipts and their strict raw state witnesses, preserving base64/length/SHA and missing/partial JSON errors. No Raw or manifest payload is involved. Exact operator/runtime manifests, safe-import list and current Linux qualification must bind the helper and protocol before any new copy/ARM/capture. Original P3/194e remains restored and CLOSED. No successor implementation, Linux qualification or deployment is supplied by this design.

## Bounded child ownership

A timeout must bound the owned helper tree, not merely wait for the runuser wrapper while leaving a descendant evaluator alive. The implementation must launch each read-only helper/unchanged CLI in its own recorded process group, capture bytes and terminate/reap only that newly owned group on timeout within a small explicit cleanup reserve taken from the same remaining warm budget. Never signal the Recorder PID/group, the whole healthy native capture group or an unrelated service. Preserve partial and final-collected stdout/stderr without duplication, record child/group identity and cleanup outcome, and fail before T0 if ownership/cleanup cannot be trusted. This is finite command ownership, not a daemon or another systemd service. A real nested-child timeout fixture is mandatory in future Linux qualification; a mocked timeout alone is insufficient.
