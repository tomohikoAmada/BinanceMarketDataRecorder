# Smallest bounded follow-up design

The immediate defect is scheduling and evidence retention in the private warm controller: it completes the required strict endpoint interval and then starts one potentially expensive canonical readiness subprocess using its independent330s timeout, with the1200s whole-warm check only afterward. The control fails closed and creates no T0, but useful canonical readiness is discarded on this honest deadline failure. The whole-warm begin/request clocks are also not published, limiting exact elapsed reconstruction. No evidence implicates classifier621 in this failure.

The narrow preferred remedy for separate implementation review is to move that one full canonical readiness call to the first current strict PASS and retain it, overlapping its work with the already required300s endpoint interval. Keep the same1200s whole-warm deadline from its original beginning, same minimum12 warm samples, same original first/end strict interval semantics, same resources/write-safety gates and same fresh prestart admission/strict start. Do not add a final duplicate full CLI call, raise thresholds or extend the failed window.

The full call must receive at most the positive remaining warm budget (also capped at its existing330s), and its result must be rejected if it returns after the deadline even when READY. Retain original stdout/stderr/returncode/parse errors or timeout bytes and before/after UTC, monotonic and BOOTTIME clocks before any failure assertion. Publish warm begin/request/absolute deadline explicitly. Persist the exact canonical READY result and bind its evidence to the same boot, Recorder invocation/PID/service instance and source/wheel/config/identity. A failed, late or mismatched result must not create a T0.

Source semantics matter: VpsReadinessEvaluator validates identity/install/systemd/process environment, reads a service snapshot and checks its heartbeat, then runs Catalog.integrity_check, and afterward evaluates products/capacity using that earlier service snapshot and captured `now`. The300s waiter bounds its polling loop but does not interrupt a single expensive evaluation. Thus neither the existing final call nor an early cached call constitutes an atomic, instantaneous readiness statement at T0. The measured115.543440s runuser session is not a measurement of Catalog time alone.

An early canonical result alone is insufficient fresh completion proof. Keep fresh strict end and start observations and bind same-incarnation continuity; explicitly validate the source's cheap dynamic predicates at completion: current active PID/invocation/no restart, published identity/profile, RUNNING/catalog-open/startup-recovered, fresh heartbeat, exact four-product topology and ready/persisted/snapshot/orderbook state, and current valid/fresh capacity observation above the hard reserve. Retain all26 strict auxiliary contexts and the existing resource/write guards. The earlier full catalog/installation/environment attestation must remain honestly timestamped; do not relabel it as a fresh full `deployment readiness` invocation at T0. This split can preserve the stage's attestation-plus-fresh-state intent under the frozen identity/same-incarnation contract, but is not literally a second full source evaluator at the endpoint. Its exact contract and implementation require independent qualification before a new attempt.

If literal full canonical evaluation at the endpoint is still required, it must fit a newly explicit reviewed phase budget/admission; simply increasing1200 or pretending cached READY is current is not justified. No alternative may reuse or extend the closed194e guard. Current stopped custody/handoff, new scope, current resources/reserves, a new finite window and new own86400 T0 remain necessary.

Required future fault cases include: exactly one full CLI after first strict PASS; preservation of old first/end300s and minimum12 semantics; READY after remaining-budget expiry; timeout and malformed output retaining original bytes; no READY result; wrong boot/PID/invocation/config/source identity; restart or stale heartbeat/capacity; bad final strict/resource/write state; short endpoint interval; and failure before T0 leaving all original observations and automatic restoration intact. These are proposed qualification cases only; no candidate, test run, copy, ARM or capture was performed here. All language/performance rewrites and CPU tuning remain deferred.
