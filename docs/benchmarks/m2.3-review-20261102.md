# M2.3 独立复核与接续完成（2026-11-02）

复核起点：`main` `8ca9f40`。本次仅完成 M2.3，不提前实施 M2.4，也不进行生产部署或在线资格验收。

## 复核结论

原交付完成了市场中立 WS 基类的提取，以及 Spot REST provenance 的反向依赖清理；但 **M2.3 尚未完成**：

- `ServiceRuntime.run()` 仍按 `config.coverage` 分别运行 `SelectedAssetCapture` 和旧 `MarketCollectorSupervisor`。
- `CoverageRuntimeSupervisor = SelectedAssetCapture` 只是命名别名。`legacy_symbols_to_coverage_config()` 尚未接入服务入口，不能构成实际的配置适配。
- 历史测试绑定 `SpotCollector/UsdMCollector` 的内部结构，应迁移为统一栈上的行为测试，不能作为保留生产双栈的验收豁免。
- 公共 WS 热路径新增的 `except TypeError` 重试回调会掩盖回调自身错误，正常 combined 回调还会先因额外参数报错再执行一次。

## 接续实现

1. 服务默认统一创建 `CoverageRuntimeSupervisor`；删除旧的采集器工厂、USD-M 全局辅助管理器及其单独的服务任务。配置只决定 source plan，不再决定监督/重连栈。
2. `collector/explicit.py` 将传统配置映射为统一计划：保留原有 Spot/USD-M 精确币种集合、四个核心 WS/REST 源、辅助源开关、轮询间隔和每进程单份全局 REST 源。不因兼容映射增加 COIN-M、K 线或其他全覆盖源。关闭 metadata 时不因发现产品额外请求目录；非标准报价币种名称也不会被基础资产猜测过滤掉。
3. 显式配置的就绪仍核对全部配置产品；只启用一个市场时不等待其他市场的目录。真正的 coverage 配置继续使用原有三市场发现及准入规则。
4. 原 5m 统计源保留 30 天初始补采、已有 Catalog 独立游标续采、有限分页、稀疏 OI 空窗口语义和 Taker 边界策略；非稀疏源空响应窗口在当前进程及重启后继续重试，超出保留期使用原 `SIDE_DATA_UNRECOVERABLE_GAP` 事件披露。响应在同一次受锁保护的 drain 中同步后，再推进游标；保留 OI `SIDE_DATA_RANGE_EVALUATED` 证据。辅助源退化阈值继续来自原配置。USD-M 两种 top-trader 公共 REST 路由加入统一客户端已有 allowlist。
5. 所有产品的异常/提前返回进入同一个监督循环，保留 `CORE_MARKET_TERMINAL_FAILURE`、停机 drain 错误传播与首个故障原因。全局源状态继续出现在原服务状态字段中；CLI 配置格式及命令入口不变。
6. WS 回调只执行一次，统一在公共层合入 receipt flags；真实 `TypeError` 直接传播。没有增加回调签名探测、异常适配框架、防御拷贝、实时磁盘回读或后台验证。
7. 历史 MS2 用例迁移到真实统一栈：fake transport 改为实际 combined 协议；验证单市场、多产品和 20 产品的精确订阅/请求范围、就绪、原始字节、全局源去重、限流门、优雅停机和 `.partial` 清空。服务故障注入仍运行同一个生产监督循环，只替换产品 worker。
8. 全量回归发现固定输入基准在启动监督器前已完成 reconcile。启动时复用已有产品任务，避免同一 spool 被两个 writer 重复消费；由原 benchmark Raw 内容一致性测试覆盖。

旧 `collector/spot.py`、`collector/usdm.py`、`collector/supervisor.py` 等直接调用兼容模块及其历史测试保留，但服务、工具和示例中已无其采集器实例化路径。外围模块延迟导入、旧模块物理清理及 Catalog 拆分属于 M2.4，未混入本次任务。
