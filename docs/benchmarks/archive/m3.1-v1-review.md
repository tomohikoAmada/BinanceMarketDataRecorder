## 一、核心结论

1. **纯代码与 I/O 架构优化收益（Arm A 基线 vs Arm B 同范围优化）**：
   - 在 **100% 相同的数据接收与落盘范围**（581,580 帧完整落盘，逻辑内容摘要 `ca0ea9d1...` 逐字节完全一致）下：

## 四、测试中发现的问题、分析与工程修正

在构建与执行三方对照基准测试过程中，发现并解决了以下重要技术细节：

### 1. 模拟时钟大步长推进对可用性监控的偶发伪断线问题
- **现象**：当以 10.0 秒为一个 tick 步长加速模拟 45 分钟采集时，`CoverageRuntimeSupervisor._observe_availability` 内置的 `now - previous > 5_000_000_000` 断线判定会被触发，将所有活跃源判定为 `MONITORING_UNKNOWN`，导致每轮 tick 重复产生恢复事件并使 transition 数量虚高。
- **原因剖析**：生产环境下 `_observe_availability` 以 1.0 秒固定周期运行，`now - previous` 始终约为 1 秒。加速模拟环境下一次性跳过 10 秒导致了监控超时逻辑的误触。
- **修正措施**：在基准驱动脚本中，在每轮 tick 触发前显式维护 `_last_monitor_utc_ns = now_ns - 1_000_000_000` 并确保活跃源的心跳戳同步更新，准确还原生产中持续处于 `AVAILABLE` 的平稳运行状态。

### 2. WS 接收帧事件的可用性账本登记对齐
- **现象**：在初版对比原型中，Arm A 与 Arm B 在将数据推入 `spool` 时未调用 `capture.availability.valid(..., checkpoint=False)`，而 Arm C 在过滤分支显式调用了该方法，导致仅 Arm C 在启动阶段触发了从 `STARTUP_UNKNOWN` 到 `AVAILABLE` 的状态转换。
- **修正措施**：对齐三组实验组的行为，所有接入帧统一触发 `capture.availability.valid(..., checkpoint=False)`，并在启动初始化阶段对全部 `source_plan` 规划源显式调用 `ensure` 与 `valid` 完成就绪注册。对齐后，Arm A 真实展现了 baseline 在 `PRAGMA synchronous = FULL` 且无检查点合并下的巨大写入压力与 21 万条积压，而 Arm B 和 Arm C 展现了 M1.2 水印合并消除积压的显著优势。

### 3. 物理分片流与资产源聚合关系对齐
- **现象**：生产配置中 `underlying_assets = ["BTC", "ETH"]` 覆盖 2,154 个理论源，但在物理写入层，WebSocket 流通过 `stream_groups(...)` 聚合成固定数量的物理流组。
- **确认事实**：通过复查 `SelectedAssetCapture` 生产映射，BTC + ETH 的 Spot、USD-M 与 COIN-M 合计映射为恰好 **85 个物理 StreamSpool**。这与 M2.2 记录中在服务启动阶段创建的 80+ 个空分片现象完全吻合，并在基准测试中完全如实反映了 Arm A 产生 85 个空分片而 Arm B/C 产生 0 个空分片的对比事实。
