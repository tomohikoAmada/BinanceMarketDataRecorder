
本机 Python 3.12.14 / macOS ARM64，13 项通过，结果见
[封存与恢复 JSON](m1.1-seal-recovery-20261102.json)：

- 以确定性随机、不同的 1 MiB 负载构造不可压缩 Raw，实际触发大小封存的分片为
  **134,274,303 bytes**；真实封存耗时 **221.74ms**。
- 封存运行于 collector 的实际 drain 线程；mock socket 继续经过 `_receive_once`、
  有界 receipt queue 与 `_writer_loop`。标称每秒 4,000 帧，实际到达由本机调度决定。
  封存期间接收 **632 帧**，receipt queue 高水位 **632 / 8,192**，等待计数与
  `IngressQueueFull` 均为 **0**；最终全部落盘，队列清空。
- **135,194,321 bytes** 的 `.partial` 扫描 **117.52ms**，尾部截断恢复 **239.99ms**，
  保留 129 条有效帧，Catalog 为 `RECOVERED`，重新扫描 clean。
- 独立子进程写入超过 128 MiB 并追加半帧，在 writer 尚未关闭时被真正 `SIGKILL`；
  重启恢复仍保留全部 129 帧，不产生虚假的已完成封存。

以上为本机离线负载证据，不外推 VPS 耗时或任意输入速率下的队列容量。

## 活跃区与 10 GiB 紧急预留

已有 `.partial` 占用已经体现在磁盘 free space 中；不能把全部活跃文件的历史占用，
再当成跨过 hard reserve 后必需新分配的临时空间。143 条流若都接近阈值，活跃区本身
约为 17.875 GiB，必须正常计入容量观测，不能声称所有流总共只占 790 MiB。

当前阻塞采集工作使用 `asyncio.to_thread` 默认 executor；Python 3.12 的 worker 数
上限为 32。停止封存时，为每个并发 worker 预算 `(128 MiB + 16 MiB 最大帧 + 12 bytes
帧前缀) × 2` 的新增压缩文件空间，不假定有任何压缩收益，总计约 **9 GiB < 10 GiB**。
未压缩源已计入现有用量，封存期间原件保留。逐流顺序封存的停机路径需求更低。

因此保留现有 `vps-production-v1` 的 10 GiB 门槛即可，无需新增容量策略、封存调度器
或后台验证。本计算针对现有默认配置与默认 executor；改大最大帧或线程池后须重新核算。
