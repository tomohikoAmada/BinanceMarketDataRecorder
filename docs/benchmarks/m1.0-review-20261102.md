# M1.0 独立复核与接续结果（2026-11-02）

结论：`884dcdd` 的基准框架接入了真实采集链路，但原报告不足以签收 M1.0。
已补齐固定输入、指标口径和落盘内容核验，重新生成 v2 基线。生产 `src/` 未改，
仍与修改前的 `f109ffc` 一致；本次只完成 M1.0，不提前实施 M1.1–M2。

## 原实现的问题与修复

| 问题 | 影响 | 接续处理 |
|---|---|---|
| `random.Random(seed)` 创建后未使用；各周期 K 线全部写成 `i=1m`，部分收盘事件时间早于收盘时间 | 参数不能定义真实的多周期固定输入 | 使用固定 RNG 生成价格；按 wire 周期、UTC/+08:00 和月历生成 bar 边界及形成/收盘序列 |
| 只遍历 `product_sources()`，同名共享组被覆盖，全局共享组无输入 | 连续合约、指数和全局流未被真实覆盖 | 从去重后的 `source_plan()` 按真实 scope 分组，覆盖 85 个 WS 组 |
| 任意前 40 次 REST 先到先得；其余响应常返回 `{}` | 请求集合取决于调度，且错误夹具不能代表正常处理路径 | 固定每个 market/stream 的代表源及所有产品深度快照，周期源轮询两次；206 次请求均须通过当前 adapter 校验 |
| 摘要只哈希 `(market, symbol, stream, record_count)` | 内容被替换仍可“复现通过” | 计时外读取全部实际 Raw，验证 checksum/hash、逐分片帧数和完整输入计数，再对规范化逻辑内容计算摘要 |
| feed 结束、Spool queue 为零时就停机 | WS receipt 队列或已取出的批次仍可能在途 | 等待每组 `received == persisted == expected`，且逐源 REST 配额全部完成；失败/超时不发布报告 |
| `BEGIN`、DML、`COMMIT` 都算“写事务”，没有区分一个事务与其中的写语句 | 写事务速率及耗时失真 | 分开统计 DML 语句、`executemany` 批次及成功提交事务；事务从 BEGIN 计到 COMMIT 完成 |
| 接收 UTC 到 append 的延迟被称为 Spool 最老等待；write 耗时被称为 append；反复关闭空 spool 也计入 seal | 指标混淆、seal p50 被空操作压低 | 用单调时钟分别测 enqueue→dequeue 与 receive→append；append/write 分开；仅真实 seal 计时 |
| 原默认 `3600s` 替换了 `60s`，却用约 1.7 秒启动/停机的全部文件数外推小时轮换率 | 无法据此证明 60 秒轮换导致的文件风暴 | 保留基线 `60s`；仅固定首次周期相位。按要求记录本次生命周期小时归一化速率，明确不作为稳态轮换结论 |
| 测试太短，没有 10 秒健康 checkpoint；RSS 混入进程前一轮峰值 | 不能证明健康日志长期积压，内存轮次也不可直接比较 | 默认至少观测 12 秒；精确记录 journal 入队峰值，当前 RSS 采样峰值与进程生命周期峰值分开 |
| 原文档与根目录两份 JSON 来自不同运行；脚本还有两处 mypy 错误 | 证据引用不一致，静态检查未收口 | 原 v1 各自归档，v2 两份完全一致，补回归并完成检查 |

摘要保留 WS exact payload bytes、原生序列/交易所时间、逻辑源、capture flags、REST 请求参数和响应内容；
仅忽略本地接收时钟、连接/请求随机身份及 D06 观测时间。内容摘要是排序后的逻辑记录哈希集合，
保留重复次数，但不绑定 UUID、压缩文件身份或并发任务之间的到达顺序。物理文件哈希另列于 `chunks`。
这次复核的完整回读只发生在离线基准结束后，没有加入生产实时路径。

## 复现方式与边界

```bash
.venv/bin/python tools/benchmark_m1_m3_pipeline.py --verify-repeatability
```

Python 环境须安装项目依赖。脚本自行读取仓库内 fixture，不依赖 `tests` 包导入或网络。
Raw 写入临时测试目录并在完成后清理，仓库中只保留 JSON 证据。

- 数据范围：50 个 BTC/ETH 产品，85 个 WS 组，`1m/5m` 两周期，13,760 个 WS 帧和 206 个 REST 观测。
- REST 使用固定配额与压缩的 100ms 重复间隔；合成限流器容量放宽，生产限流配置不变。
- 保留修改前的 `60s / 128 MiB`、`WAL + FULL`。首次轮换固定为 writer 打开后完整 60 秒，避免宿主机 uptime 相位改变短突发分片数。
- 计时包含目录 reconcile、启动空分片、WS/REST、可用性扫描/刷盘、优雅停机与封存；排除导入、fixture 构造、Catalog 建表和结束后的 Raw 核验。
- 未启动服务层后台校验、日报/容量监控或外部归档。fsync 分布只计 Raw writer fsync，压缩文件和目录同步包含在 seal 总耗时中。
- 这是包含至少 12 秒监控的固定突发基线，不是全默认周期生产配置、不是真实请求频率，也不能证明稳态吞吐上限、轮换收益、长期积压或生产资格。
- v1→v2 改变了输入覆盖、计时边界和统计口径，两者性能数字不可直接作优化对照。M3.1 仍必须在相同输入/硬件下完成 45–60 分钟三组实测。

下一步 M1.1 需要跨轮换输入验证收益。另有文档口径差异：当前 `AGENTS.md` 规定 64 MiB，
计划 M1.1 写 128 MiB；本次仅记录现有代码的 128 MiB 基线，不据此更改后续要求。
