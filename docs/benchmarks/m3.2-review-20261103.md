    - 写入耗时：**`54.868s`**

    - 扫描耗时：**`17.006s`**
    - 扫描吞吐：**`58,804.2 帧/秒`**

    - Python 堆内存峰值（`tracemalloc`）：**`0.012 MiB`**（`12,384 字节`，远低于 `64 MiB` 安全红线）

- **全量 Stress 套件验证**：运行 `python3 -m pytest -m stress -v`，包含 100 次阻塞取消竞争、1M 事件写入、1,000 次重连轮换周期及 100 次背压边界测试，**5 项全部通过（耗时 86.97s）**。

### 2.4 专项故障恢复测试

针对 M3.2 明确要求的两项关键故障恢复场景，已在 [`tests/integration/test_m3_2_fault_recovery.py`](../../tests/integration/test_m3_2_fault_recovery.py) 建立专门的集成测试矩阵（7 passed in 7.05s），并结合既有专项套件通过验证：

1. **SQLite WAL 尾部回滚对账测试**（`test_sqlite_wal_tail_rollback_reconciles_sealed_and_partials`）：
   - **场景模拟**：在 `PRAGMA synchronous = NORMAL` 下，子进程持续写入分片并封存，随后未执行 checkpoint 直接被 `SIGKILL` 终止；父进程实际截断 SQLite `-wal` 文件尾部字节，模拟掉电丢失最后数秒 `Catalog` 提交，此时磁盘上已存在完整的 `.zst` + `.json` 分片文件或未完成的 `.partial` 残留。
   - **恢复验证**：覆盖 `Catalog` 缺失记录、记录为 `ACTIVE`、记录为 `SEALING` × 磁盘有/无残留 `.partial` 共 6 种故障组合。
   - **恢复结果**：`recover_storage()` 自动根据磁盘上已验证的分片前滚将 `Catalog` 状态对账为 `SEALED`，正确清理多余 `.partial` 文件，保留唯一的单分片有效记录，可用性账本诚实计入丢失的 12 秒 `unknown` 窗口，且重复执行恢复具备幂等性。
2. **K 线断线跨整点 REST 补采测试**（`test_kline_disconnect_across_close_boundary_backfills_without_gap`）：
   - **场景模拟**：WebSocket 采集流正常接收第 0 分钟收盘 K 线（`openTime = 0, closeTime = 59_999, x = True`）；在 `110s` 时模拟网络中断（此时第 1 分钟 `openTime = 60_000` 尚未收盘）；断线持续跨过 `119_999` 整点收盘边界，并在 `125s` 时重连成功。
   - **补采验证**：重连生命周期钩子立即检测到预期收盘点 `60_000` 错失，自动向共享调度队列发起 REST `/klines` 补采请求（参数 `startTime = 60_000, endTime = 119_999`）；
   - **标记与连续性核验**：
     - 补采结果打上 `capture_flags = ("closed_bar_backfill",)` 标记，并记录真实的 REST 接收时间（`receive_time_utc_ns >= 125s`）；
     - WebSocket 流恢复后继续接收第 2 分钟收盘 K 线（`openTime = 120_000, closeTime = 179_999, x = True`）；
     - 持久化收盘 K 线序列开盘时间依次为 `[0, 60_000, 120_000]`，相邻周期严格满足 `open_time[i+1] == open_time[i] + 60_000`，**全序列无漏收、无断点**。
3. **既有故障注入全量套件**：`tests/fault_injection/` 全部 86 项测试（含跨卷归档 `SIGKILL`、Catalog 快照回滚、订单簿序列跳变、随机损坏注入等）全部通过（5.31s）。

## 三、 发现的问题与修正

1. **`test_million_events.py` 指标测量未结构化记录**：
   - **根因**：原脚本仅断言 `tracemalloc` 峰值小于 64 MiB，未记录写入与扫描耗时，亦未暴露进程最大 RSS。
   - **修正**：在 `tests/stress/test_million_events.py` 中引入 `time.perf_counter()` 与 `resource.getrusage()`，分别精准计时写入 1M 事件与扫描 1M 事件的耗时及 FPS，并在保留原断言的基础上，向 `docs/benchmarks/m3.2-stress-million-20261103.json` 导出结构化数据。
2. **专项故障恢复测试分散与缺少一体化用例**：
   - **根因**：虽然 M1.2 和 M1.3 单测中已各自包含 WAL 截断与补采函数，但在端到端故障注入集成层缺少一个一键验证全部 M3.2 故障门禁的入口。
   - **修正**：编写 [`tests/integration/test_m3_2_fault_recovery.py`](../../tests/integration/test_m3_2_fault_recovery.py)，将掉电回滚矩阵（6 组合）与跨整点断线补采无缺口恢复集中交付，并确保通过 Ruff、strict mypy 与离线集成回归。
3. **文件末尾多余空白行**：
   - `git diff --check` 检出 `test_million_events.py` 末尾存在多余换行符，已在提交前完成清理。
