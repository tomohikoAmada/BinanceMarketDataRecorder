# M1.2 独立复核与补齐（2026-11-02）

复核起点：`main` / `ecf0302dc4f7eace4158ec195dea2784ce84fcf4`。
范围为生产计划 M1.2；保留原设计，补正具体顺序、归属、恢复和验收缺口。
本次不部署 VPS、不实施 M1.3–M2，不改变 Raw v1。

## 结论与原实现缺口

原实现的主要方向正确：Catalog 默认 `WAL + NORMAL`、关键删除 `FULL` 屏障、
Journal checkpoint 合并、共同水位表和封存文件恢复前滚均已存在。
但原“严格验收完成”不能直接签收，问题及补正如下：

| 原问题 | 后果 | 本次处理 |
| --- | --- | --- |
| 有界 flush 提前退出后仍提交 watermark | 尚未持久化的故障可能被健康水位掩盖 | 队列未排空不提交 watermark，最后一批可与水位同事务提交 |
| 事务成功前更新 `_last_watermark_flush_utc_ns` | 失败重试可能跳过本轮检查点 | 提交成功后确认当次捕获的时间 |
| 未到水位周期时 checkpoint 直接逐源写盘 | 周期错位仍会产生数千条冗余写入 | monitor 模式始终只写真实跳变；独立 Journal 接口保留 |
| 查询把某一水位应用于全部历史源 | 旧资产选择或旧配置中的源被虚假计为健康 | 在现有源 JSON 中记录 owning selection，水位键含本次 instance；各源只读自己的水位 |
| 查询还推进 `last_valid_utc_ns` | 读取结果混淆监控确认和原始有效观测时间 | 只投影 `observed_at_utc_ns` |
| 新增 `.partial` 清理盲目 unlink Catalog 路径，兜底 UUID 含连字符 | 可能误清理其他路径，且找不到正常 Writer 的 UUID hex 文件 | 使用实际 Writer 文件名，复用既有恢复内容/身份校验清理函数 |
| 强同步事务的 `BEGIN` 在 finally 之外 | BEGIN 锁失败后连接留在 FULL | 将 BEGIN 纳入还原 NORMAL 的 finally 范围 |
| 原规模测试仅 200 个模拟源 | 不支持原文“真实 BTC+ETH 4,660 源实测” | 直接用 4,660 个模拟健康源执行真实监控、Catalog 与 SQL trace |
| 原 WAL 测试仅 SQL 回改状态 | 未验证实际 WAL 恢复或缺记录/SEALING 情形 | 新增杀死子进程后截断真实 WAL 的六组测试 |
| 原专项文件有 6 项 mypy 错误 | 不符合项目静态检查要求 | 修正枚举导入、transaction id 类型及 ignore 标注 |

## 实现边界

- 不增加新模块、后台任务、周期复查、磁盘边界文件、额外深拷贝或 live readback。
- 继续使用 `AvailabilityJournal` 原 FIFO 和原地合并字典，故障、恢复、失败计数、
  suspend/resume 仍为有序跳变。生产 flusher 在内存中确认健康 checkpoint，
  只有跳变写逐源状态；健康水位每 10 秒一次。
- `selection_id = assets:<排序资产>:<collector_instance_id>`，写在已有源状态 JSON 中。
  一次监控观察当前全部源；新增源先有 startup/恢复跳变，再获得水位覆盖；
  lifecycle dormant 源不通过水位推进。每个新实例使用自己的水位，旧实例源不会跟随新水位。
  重启加载时各源恢复前一实例已确认的边界。旧版无 membership 的记录保守使用自身时间。
- 本地删除授权及完成继续用 `_transaction(force_sync=True)`；远端授权也用此入口，
  远端完成保留原专用 FULL 事务。原文“四项全部统一用 `_transaction`”不符合实际代码。
- `NORMAL` 可在 OS 崩溃/掉电后丢失最近已提交元数据，不承诺物理断电零损失；
  已封存文件与 manifest 可恢复 Catalog，监控尾部未知区间不会被补成健康。

## 可复现验收

专项文件：`tests/unit/test_m1_2_catalog_and_availability.py`，共 **17 项通过**。

1. **规模及真实 SQL 写入**：4,660 个健康模拟 WS 源与 3 个默认目录源，先完成初始登记，
   再逐秒观察 10 秒。每轮 flush 后 pending 为 0；SQL trace 仅有 **1 条 watermark
   INSERT/UPSERT、0 条逐源 INSERT/UPDATE**，相对健康 checkpoint 的 4,660 行下降 99.98%。
   目录源的初始失败状态不计为健康源，其故障登记属于初始事务。
2. **水位提交顺序**：分别触发批数上限和时间上限；末尾仍有 outage 跳变时，
   durable watermark 和内存已提交时间都停在旧值；排空后才推进。
   注入 watermark 事务失败后，pending 和重试资格保持。
3. **归属与未知尾部**：不同 selection 和无 membership 的历史源各使用自己的边界；
   continuity report 保留精确 unknown 尾部，`last_valid_utc_ns` 不被查询改写。
4. **真实 WAL 尾部丢失**：子进程关闭自动 checkpoint，写入非空 Raw、封存 manifest 与新水位；
   父进程 `SIGKILL`，将真实 WAL 截断到先前提交边界，再重新打开 SQLite。
   **缺记录 / ACTIVE / SEALING × 有 / 无重复 partial** 六种情况均恢复为 SEALED，
   保留一条有效 Raw 记录，活动目录无遗留 partial，再次恢复幂等。
   旧水位到恢复时刻的 **12 秒（丢失 10 秒监控尾部 + 2 秒停机）** 全部记为 unknown。
   原 SQL 回改测试保留并明确更名为逻辑 stale-state 测试。
5. **删除与清理**：本地两个删除状态验证 FULL、checkpoint、还原 NORMAL；
   远端真实授权/删除路径验证 `FULL → BEGIN → COMMIT → PASSIVE → NORMAL` 顺序，
   授权完成前 Raw 不被删除。另覆盖 BEGIN 锁失败还原，以及 UUID hex 重复 partial
   清理时保留 Catalog 误指向的无关文件。
6. **原有语义回归**：P3 可用性、lifecycle、时钟回拨、RPI、故障注入、归档恢复与
   远端授权/删除测试继续运行，确保原始 gap 和状态边界不变。
