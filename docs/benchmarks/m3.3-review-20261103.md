## 使用及边界

观察器为独立运维脚本，不包含在业务 Wheel 中。M4 部署时同时取当前提交中的 `tools/observe_vps_recorder.py`（可配合 `scripts/observe-recorder`），使用已安装 Wheel 的解释器或显式 `--cli-path`。冻结 JSON 记录了两者摘要。

```bash
scripts/observe-recorder --config /etc/binance-market-data-recorder/recorder.toml --once
scripts/observe-recorder --config /etc/binance-market-data-recorder/recorder.toml --interval 10 --output /var/log/recorder-observer.jsonl
```

分片增长率是从首样本起的**本地留存分片数/字节净增加率**，下降时按零记录；若归档同时退休源文件，不能据此推断累计生成量。CPU 第一条是基线，后续按单核 100% 的 CPU 时间差计算；采样周期包含外部命令耗时。脚本只查看元数据和既有 `status`，不做 Raw 内容重验或服务控制。

systemd 字段解析由离线回归覆盖；macOS 端实际走缺失 systemctl 与 `ps` 路径，不宣称已验证 Linux systemd。Linux 生产路径权限、宿主机架构/容量和真实在线观测留给 M4.1；P4 历史主机记录与当前计划的规格存在差异，届时应重新读取宿主机事实。本次没有 SSH、启动/停止服务或更改历史生产数据。

## CI 接续修正（2026-11-03）

提交 `2481700` 的 [CI run 41564104623](https://github.com/tomohikoAmada/BinanceMarketDataRecorder/actions/runs/41564104623) 中 Ubuntu 全流程通过，macOS 离线套件为 **1 failed / 2565 passed / 24 skipped / 5 deselected / 13 warnings**。唯一失败是 `test_recovery_completion_observes_capacity_before_collectors_and_reuses_heartbeat`，在读到 RUNNING 后立即断言全部 collector 的 `started` 为真。

服务的 RUNNING 状态发布与 collector 子协程的首次调度是两个独立时点。原测试只等待前者，CI 调度下后者可能尚未发生；这不是采集配置或生产启动顺序变化。在本机给 FakeCollector 首次执行加入 50ms 调度延迟，原测试在同一断言处复现失败。

修正只涉及该测试：在原有有界轮询中同时等待 RUNNING 和全部 collector 已启动，保留 recovery → capacity → collector factory 的顺序断言、恢复完成和唯一 heartbeat owner 检查；用 `finally` 保证失败时也停止服务任务。参数化覆盖无额外延迟和 50ms 延迟两种调度，不增加生产等待、重试或防御层，不改 Wheel/配置/观察器摘要。

修正后的两种调度专项通过（2 passed）。最终本机检查记录在冻结 JSON 的 `ci_followup` 中；修正提交的 GitHub Actions 是另一次独立验证。

本次本机最终门禁：**2567 passed, 24 skipped, 5 deselected, 13 warnings in 224.57s (0:03:44)**；服务专项 29 passed；Ruff、strict mypy（386 文件）、M0、Go Raw golden 和差异检查通过，仍仅有原 13 条 fork 弃用警告。
