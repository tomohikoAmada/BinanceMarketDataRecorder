## 三、 发现的问题与深度根因定位（有哪些问题）

在 M4.1 实施与初始起跑观测中，发现了以下 5 个具体问题，并已完成诊断与闭环处置：

### 问题 1：macOS 本地 Surge 增强模式（utun4）阻断 SSH 22 端口通信
- **现象**：本地执行 `ssh greencloud-tokyo-01` 报 `kex_exchange_identification: Connection closed by remote host`。
- **排查根因**：本地 Surge 开启了 Enhanced Mode，全局创建虚拟网卡 `utun4` 并拦截全部出站流量。由于 Surge 未配置直接放行该 VPS 的裸 TCP 22 端口，连接被本地代理层直接 RST 关闭。
- **解决方案**：编写专用代理跳板脚本 [`tools/ssh_en0_proxy.py`](../../tools/ssh_en0_proxy.py)，利用 macOS Darwin 提供的 `IP_BOUND_IF = 25` socket 选项强制将出站流量绑定到物理网卡 `en0`，绕过 `utun4`；并在 `~/.ssh/config` 中配置 `ProxyCommand`，实现透明秒级直连。

### 问题 2：宿主机硬件架构与计划文档描述不一致
- **现象**：`production_milestone_plan.md` 描述目标机为 `Ubuntu 24.04 ARM64, 2 vCPU, 4 GB RAM`。
- **实测事实**：`uname -m` 为 `x86_64`，`lscpu` 为 `4 vCPU Intel Core Processor (Broadwell) @ 2.0GHz`，物理内存为 `5,878 MiB`（~5.74 GiB）。
- **影响评估**：x86_64 相比原估算的 ARM64 具备更强的单核性能与双倍 vCPU（4 vCPU），且内存富余更充分；在生产配置与压测中均完全满足要求。已在文档中明确勘误。

### 问题 3：生产配置 `vps-production-v1` 强校验部署身份
- **现象**：服务首次直接拉起时报 `DeploymentIdentityError: configuration SHA-256 mismatch`。
- **排查根因**：根据系统设计，在 `vps-production-v1` 配置档位下，守护进程启动必须严格核对 `/etc/binance-market-data-recorder/deployment-identity.json` 中的各文件哈希与属主权限（防止配置或包被未授权改动）。部署新 Wheel 和配置后，需重新签发并校验部署凭证。
- **解决方案**：以 root 权限执行 `deployment identity-create` 并运行 `deployment verify`，确认状态为 `VERIFIED` 后启动。

### 问题 4：远期交割合约无实时撮合成交导致 product.ready 统计等待
- **现象**：`cm_delivery` 下的远期合约（如 `ETHUSD_270326`）深度快照与订单簿同步已完成（`syncd=True, snap=True`），但 `ready=False`。
- **排查根因**：远期交割合约市场极少有连续实时交易，其 `agg_trade` 流在启动阶段未收到任何成交帧。根据既有产品准入合同（P4 记录），“安静流不以尚无首笔成交判失败”；只要订单簿已桥接同步且数据源状态正常，即属正常采集行为。

### 问题 5：高并发启动期队列写放大导致服务崩溃重启（关键瓶颈定位）
- **现象**：首个服务实例（PID 4155）运行至 `03:01:51 UTC`（运行约 8 分钟）时退出并被 systemd 重启（生成 PID 6755，`NRestarts=1`）。日志记录关键异常：
  ```text
  RuntimeError: availability journal exceeded its bounded persistence queue
    File "binance_market_data_recorder/collector/coverage.py", line 1602, in run
      self._observe_availability(now)
    File "binance_market_data_recorder/collector/coverage.py", line 1556, in _observe_availability
      self.availability.unavailable(key, now, "MONITORING_UNKNOWN", since=previous)
    File "binance_market_data_recorder/collector/availability.py", line 91, in _emit
      raise RuntimeError("availability journal exceeded its bounded persistence queue")
  ```
- **深度代码与数学根因**：
  1. 在 `collector/coverage.py` 第 1555–1556 行：
     ```python
     if previous is not None and (now < previous or now - previous > 5_000_000_000):
         self.availability.unavailable(key, now, "MONITORING_UNKNOWN", since=previous)
     ```
     在启动初期或 50 个产品深度快照并发注入时，主事件循环单轮调度延迟若短暂越过 5 秒阈值（`now - previous > 5s`），该逻辑会对全量 **4,660 个活跃数据源**逐一调用 `self.availability.unavailable(key, now, "MONITORING_UNKNOWN")`。
  2. 由于 `unavailable` 被标记为状态跳变（`is_transition=True`），它无法在内存字典中原地合并，而是强制向 `self.pending` 队列追加 4,660 条记录。
  3. 紧随其后的常规可用性判定（第 1572–1574 行）发现正常 WebSocket 源状态良好，立即对这些源调用 `self.availability.available(key, now)`，再次触发 recovery 跳变，又向 `self.pending` 追加数千条记录。
  4. 单次循环就向待写队列注入了接近 10,000 条未合并条目；而 `_flush_availability()` 受限于每次 100ms 的刷盘配额（最多刷 32 批 × 128 = 4,096 条），多轮突发叠加导致 `self.pending` 队列迅速冲破 65,536 上限并抛出异常。
- **与历史记录交叉印证**：此现象与 2026-11-01 `P4 Run C`（单 BTC 时待写队列增至 52,997 条）表现出的根因完全一致。双币种（`BTC + ETH`）规模下单币源翻倍至 4,660，使得该放大效应成倍加剧。
- **后续优化方向（M4.1 修复与重启计划）**：
  - 优化 `MONITORING_UNKNOWN` 判定：当触发循环监控延迟时，通过全局水位或批量跳变合并，避免对数千个正在健康接收 WS 的源产生“瞬时标记未知后立即恢复”的乒乓跳变放大；
  - 增强 `_flush_availability` 在积压期间的排水弹性；
  - 修复后按规则重置 `T0`，开始连续 24 小时 `NRestarts = 0` 正式资格跑。
