## 三、 发现的问题与深度根因定位（有哪些问题）

在 M4.1 实施与初始起跑观测中，发现了以下 5 个具体问题，并已完成定位与代码级修复闭环：

### 问题 1：macOS 本地 Surge 增强模式（utun4）阻断 SSH 22 端口通信
- **现象**：本地执行 `ssh greencloud-tokyo-01` 报 `kex_exchange_identification: Connection closed by remote host`。
- **排查根因**：本地 Surge 开启了 Enhanced Mode，全局创建虚拟网卡 `utun4` 并拦截全部出站流量。由于 Surge 未配置直接放行该 VPS 的裸 TCP 22 端口，连接被本地代理层直接 RST 关闭。
- **解决方案**：编写专用代理跳板脚本 [`tools/ssh_en0_proxy.py`](../../tools/ssh_en0_proxy.py)，利用 macOS Darwin 提供的 `IP_BOUND_IF = 25` socket 选项强制将出站流量绑定到物理网卡 `en0`，绕过 `utun4`；并在 `~/.ssh/config` 中配置 `ProxyCommand`，实现透明秒级直连。

### 问题 2：宿主机硬件架构与计划文档描述不一致
- **现象**：`production_milestone_plan.md` 描述目标机为 `Ubuntu 24.04 ARM64, 2 vCPU, 4 GB RAM`。
- **实测事实**：`uname -m` 为 `x86_64`，`lscpu` 为 `4 vCPU Intel Core Processor (Broadwell) @ 2.0GHz`，物理内存为 `5,878 MiB`（~5.74 GiB）。
- **影响评估**：x86_64 相比原估算的 ARM64 具备更强的单核性能与双倍 vCPU（4 vCPU），且内存富余更充分；在生产配置与压测中均完全满足要求。已在文档中明确勘误。

### 问题 3：生产配置 `vps-production-v1` 强校验部署身份
- **现象**：服务拉起前必须核对部署身份凭证，否则报 `DeploymentIdentityError`。
- **排查根因**：根据系统设计，在 `vps-production-v1` 配置档位下，守护进程启动必须严格核对 `/etc/binance-market-data-recorder/deployment-identity.json` 中的各文件哈希与属主权限（防止配置或包被未授权改动）。部署新 Wheel 和配置后，需重新签发并校验部署凭证。
- **处置**：执行 `deployment identity-create` 并运行 `deployment verify`，确认状态为 `VERIFIED` 后启动。

### 问题 4：远期交割合约无实时撮合成交导致 product.ready 统计等待
- **现象**：`cm_delivery` 下的远期合约（如 `ETHUSD_270326`）深度快照与订单簿同步已完成（`syncd=True, snap=True`），但 `ready=False`。
- **排查根因**：远期交割合约市场极少有连续实时交易，其 `agg_trade` 流在启动阶段未收到任何成交帧。根据既有产品准入合同（P4 记录），“安静流不以尚无首笔成交判失败”；只要订单簿已桥接同步且数据源状态正常，即属正常采集行为。

### 问题 5：事件循环过度线程调度诱发 Pong 超时断线与可用性队列溢出崩溃（关键瓶颈与代码修复）
- **现象**：首次尝试运行中，PID 4155 与重启后的 PID 6755 均在运行约 7–8 分钟时抛出 `RuntimeError: availability journal exceeded its bounded persistence queue` 异常崩溃退出。
- **深度代码与因果链定位**：
  1. **Idle REST Spool 轮询线程风暴**：在 `collector/coverage.py` 第 1658–1665 行，事件循环在每 100ms 的空闲等待（`wait_for(stop.wait(), timeout=0.1)`）间隙中，无节制地遍历全部 `rest_observations` 分片（20~30 个），并对每个分片调用 `await run_owned_blocking_call(spool.drain_all)`。这导致每秒创建并等待数百个线程池任务，严重争抢 Python GIL 并阻塞 asyncio 事件循环调度。
  2. **Binance WebSocket Pong 超时断线**：由于事件循环被线程池密集调度占用，WebSocket 心跳响应无法在 Binance 规定的 10~20 秒窗口内及时发出，Binance 服务端以 `1008: "Pong timeout"` 强制切断 WebSocket 连接（日志中清晰记录 `ETHUSDT` 与 `BTCUSDT` 出现 `Pong timeout` 断线）。
  3. **可用性状态机乒乓跳变**：断线重连与事件循环卡顿触发了 `_observe_availability` 的监控延迟分支（`now - previous > 5s`），对全量活跃数据源批量标记 `MONITORING_UNKNOWN` 并随后立即标记 `valid`，单次注入数千条 transition。
  4. **固化刷盘超时导致队列只增不减**：`_flush_availability()` 设有了 `0.1s` 的硬性超时上限（`AVAILABILITY_FLUSH_SECONDS = 0.1`）。在积压发生时，每次只能刷约 600~1,000 条即退出，导致队列每轮 tick 净增数千条，迅速越过 65,536 容量上限而崩溃。
- **工程级解决方案落地**：
  1. **REST Spool 轮询节流**：在 `coverage.py` 中引入 `self._last_rest_spool_drain`，将无数据的 idle REST spool 检查频率从每 100ms 降至 **每 5.0 秒一次**，削减了 98% 的冗余线程池创建与调度开销，消除了事件循环阻塞与 Pong 超时断线根源。
  2. **可用性待刷队列弹性排水**：在 `_flush_availability()` 中，当 `len(self.availability.pending) > 2048` 出现积压时，允许放宽 0.1s 耗时限制，最多刷 128 批（每批严格保持 128 条上限），确保积压在 1~2 个周期内被完全排空至安全水位以下，绝不堆积至 65,536。
  3. **单元回归与契约保障**：新增单元测试 `test_emergency_backlog_drains_without_queue_overflow`，全量回归 2,566 个离线测试、Ruff 与 mypy 100% 通过；重新打包 Wheel、更新冻结元数据并部署。
