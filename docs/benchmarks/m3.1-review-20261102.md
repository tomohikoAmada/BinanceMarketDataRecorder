# M3.1 独立复核与接续（2026-11-02 至 2026-11-03）

## 复核结论

`16dd806` 提交的 M3.1 **未满足验收要求**；现已接续完成真实 45 分钟 × 3 对照及离线审计。原报告和 JSON 已原样保存在
[`archive/m3.1-v1-review.md`](archive/m3.1-v1-review.md) 与
[`archive/m3.1-v1-three-way.json`](archive/m3.1-v1-three-way.json)。其中的
4.45x、21 万条稳态积压、内存泄漏与 VPS 余量结论不能作为验收证据。

发现的具体问题：

1. **持续时间不符**：A/B/C 实际只运行约 49/23/11 秒，用 10 秒一次的测试时钟
   模拟 45 分钟。M1.1 已明确这种测试不能替代 M3.1 的墙钟持续运行。
2. **基线不真实**：A 在优化后的生产代码上修改参数、替换 Journal、手工制造空分片并
   模拟回读，没有运行 `f109ffc` 的 Writer、REST 路径或服务监控调度。
3. **输入绕过生产逻辑**：各类 WS 都被简化为类似 trade 的消息，K 线没有原生 `k`
   字段；直接构造 EventEnvelope 入 Spool，绕过解析、序列检查、实际 D1 过滤和
   有界 WS 接收队列。虽然构造了 MockRestClient，实际没有任何 REST 轮询和补采。
4. **健康状态与积压人为化**：每次推进 10 秒只 flush 一轮，又直接重置监控及成功时间，
   与生产每秒监控、约每 100ms 执行主循环不同。原基线已有每轮最多 4096 行/100ms 的
   刷新能力，不能据此模拟结果断言生产存在 21 万条积压。
5. **指标口径错误**：persist_lag 在 enqueue 后两个相邻计时调用之间采样，未测到写盘
   完成；queue_wait 测的是 enqueue 调用本身；fsync 通过每轮 drain 人工加一；写入
   字节数混加 payload 长度与压缩产物，遗漏 Raw framing/metadata 和 manifest。
6. **资源结论不成立**：三组在同一进程连续执行，RSS 受上一组及离线解码的内存分配影响；
   最大封存数所在分钟的平均 CPU 也不是轮换窗口峰值。macOS 的加速离线测试不能证明
   GreenCloud 2 vCPU/4GB 的生产余量，短测 RSS 增长不能证明泄漏。

## 接续方案与测量边界

只修改基准工具、必要测试和证据文档；不修改 `src/`，不增加运行时防御或校验层。

```bash
.venv/bin/python -m tools.benchmark_m3_three_way \
  --duration-seconds 2700 \
  --output-json docs/benchmarks/m3.1-three-way-benchmark.json
```

- A/B/C 在相同机器上**顺序**运行，每组使用新的 Python 3.12 进程、独立 Catalog 和
  文件目录，各真实运行至少 2700 秒，不修改任何生产时钟。
- A 从 Git 导出 `f109ffc` 的 `src/`，运行其实际采集、Writer、Catalog 与封存逻辑。
  原 `verify_new` 通过独立 owned thread 并行执行，复用真实验证队列；CPU/RSS 为整个
  测试进程的合计值。生产中的独立验证进程拓扑没有在本基准复制，不能用此 RSS 比较
  推断独立进程的总内存差异。B/C 不启动实时回读或后台重验。
- B 使用当前代码，恢复全部 S12 周期与全部形成帧写盘，并关闭 D1 自动补采
  以保持 A 的原始落盘范围；C 使用默认 D1/D2 生产策略。
  保留实际 60s/900s 轮换、128MiB 上限、流间 hash 相位和独立 1s durability。
- 网络对端离线模拟：固定 BTC/ETH 目录、50 个产品，原生 WS payload 每 wire 每秒一帧，
  REST 包含各具体 source，并按原声明 cadence 安排有限请求槽位；参数使用固定样本时间。
  跳过已经完成配额的重复请求，不按速度改变输入量；公共 API 的 IP 网络配额在离线
  mock 中放宽，不代表可在线使用该请求速率。
- 所有 WS 经过生产连接接收、有界队列、解析、序列检查、过滤、Spool 和 Writer。
  REST 经过实际 capture/validate/persist 路径。源码不注入健康状态，不手工产生空分片。
- 三组均漏发 Spot BTCUSDT 的第 120 秒 `1m` 收盘帧。C 在下一次收盘时自动识别缺口并
  执行实际 REST 补采；检查 `closed_bar_backfill`、正确开收盘区间和真实接收时间。
  此处验证漏收后的补齐；断线重连专项另由已有 M1.3 回归覆盖。
- CPU/RSS 每秒采样，CPU 的 100% 表示占用一个核；轮换峰值取真正发生 seal 的采样
  窗口。分分钟记录接收/落盘/过滤数量、文件数、写入字节与延迟分布。
- queue_wait 为实际 enqueue→dequeue；persist_lag 为实际接收→append 返回后的持久化回调；flush、
  SQL statement/transaction、Raw fsync、seal 独立计量。延迟先量化为微秒再累计分布，
  每分钟先切换样本列表再汇总，避免并发追加时丢样；不保留全部历史逐事件延迟。
  RSS 仍包含直方图、每秒时间线、mock 生成和统计器开销，不能用它证明生产进程绝对零泄漏。
- 字节数为实际 Python write/writev（Raw、manifest、锁文件）加单独压缩输出，**不是**
  物理块设备写入；SQLite C 层写入/fsync、OS 缓存和写放大不包括在该口径中。
  fsync 统计实际 Python 调用，包含目录与封存，不能解释为整机所有 fsync。
- 采集停止后离线验证每个产物的 manifest/hash/CRC/frame count，无遗留 partial。
  对实际解码 Raw 与预期输入比较帧数和 `sum(SHA256) mod 2^256` 多重集指纹，避免
  在线程/分片顺序上制造伪差异；该指纹不是文件 SHA-256。逐分片的标准 SHA-256 另行保留。
  A/B 还必须具有相同 WS 输入、相同 WS Raw payload 和相同 REST 逻辑内容。
- 合成输入率不代表 Binance 峰值。macOS CPU、RSS 和吞吐仅证明本机该负载的运行表现；
  VPS 连续在线资格仍由 M4 判断。不能为达到预设结论而制造旧基线积压。

### 结果解释与准出

- **A → B 代码与 IO 路径收益**：相同 WS 输入/WS payload/REST 逻辑内容下，
  CPU 总耗时减少 **12.52%**；生命周期分片减少 **90.46%**；Catalog 写事务减少
  **88.65%**；Availability flush 总耗时由 **76.968s → 18.618s（-75.81%）**，
  seal 总耗时由 **100.004s → 19.695s**。未复现原报告的 21 万条持续积压；
  真实 A 仅一次稳态每秒采样末仍有 1390 行，下一秒回零，B 的 2400 个稳态采样末均为零。
- **代价也保留**：B 单片更大，seal p99 从 146.181ms 增至 199.486ms，但调用次数
  大减。应用写入字节数和 Python fsync 次数没有下降；新的 K 线解析元数据
  `klineClosed/openTime/closeTime/interval` 仍写入 B 的 Raw，未压缩体积由
  4838.128MiB 增至 5105.624MiB。不能把“文件更少”表述为所有 IO 指标都改善。
- **B → C 范围收敛收益**：WS 接收量减少 **14.39%**；Raw 总帧数减少 **75.76%**；
  应用写入字节减少 **78.56%**；CPU 总耗时进一步减少 **16.73%**（相对 A 合计减少
  **27.16%**）。三组都运行满 45 分钟，不能把固定时长对照表述为墙钟 4.45x 加速。
- **C 稳态与内存边界**：第 5–45 分钟全部 2400 个每秒采样末和期间单次 flush 返回
  均无未刷余量；最后 15 分钟 RSS 217.281–235.078MiB，停机末样本 265.828MiB，
  无队列堆积造成的内存失控。曲线包含统计器/分配器开销且有缓慢增长，不能以此证明
  长期绝对零泄漏；该合成负载下本机资源占用较低，VPS 的实际 CPU/内存余量仍由 M4 核验。
- **完整性**：三组共 7,849 个分片全部离线审计通过，0 遗留 partial、0 畸形夹具帧；
  C 的 60,770 条 REST 中，60,769 条为确定配额，1 条为实际自动缺口补采。
  所有输入槽位、所有产物和每帧持久化观测一致。网络是 mock，本记录不证明真实 Binance
  逐源 99.5% 可用率、接口适用性或服务 24h 内存稳定性。
