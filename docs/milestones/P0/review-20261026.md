## R1 · 中优先级：排序后核对掩盖实际写入乱序

位置：[steady_baseline.py](steady_baseline.py#L400)，400–424 行；尤其 402–408 行。

核对器先按 `receive_monotonic_ns` 给所有记录重新排序，再和输入摘要比较。因此，同一连接的帧若收到顺序为 1、2、3，却被 writer 写为 2、1、3，只要各帧带着原接收时间，当前比较仍通过。注释还把 `load_source_chunks` 说成按流时间排序，实际该 helper 按内容哈希 / chunk ID 排序。

本次使用真实 `RawChunkWriter`、`seal_partial`、`load_source_chunks`、`iter_source_records`，在独立临时目录写入三个合法测试事件，物理顺序为 2、1、3。完整文件读取及校验成功；直接比较物理原文顺序为 false，执行基准中的排序后比较为 true。接收单调时间依次为 `[5000000002, 5000000001, 5000000003]`。没有访问生产数据。

影响：P1 正要修改批量写入和并发处理，这个核对器会遗漏一类相关回归。现有结果可以支持原文内容与数量核对，不能凭该步骤证明物理写入顺序从未改变。

- [ ] **修正 / 通过条件：**保留物理帧 ordinal，先独立检查同一连接 / 流的写入顺序，再按明确的 chunk 生命周期拼接核对输入；需要排序的回放语义与原始写入顺序分开报告。增加 2、1、3 乱序应失败、正确跨分片顺序应成功的短回归。不要仅把 sort 换成另一个按帧内容重排的 sort。

## R2 · 中优先级：计时窗口之外补做的工作没有从性能结论中区分

位置：[steady_baseline.py](steady_baseline.py#L364)，364–377 行及 459–467 行。

脚本先在固定时间记录 `after` / `STEADY_END`，之后才最多再等 60 秒把全部输入送完，再正常停止、排空和验证。窗口开始 / 结束未保存每流已发送、已接收、已持久化数量及队列字节；结尾检查的是最终总量。输入源还会在落后时赶发，所以一个处理更慢或延迟写入的候选，可能把部分工作移到计时外完成，仍输出同样的最终正确性标记。

这是代码路径和测量口径缺口，**不是声称当前两轮已经出现了持续积压**。现有结果不足以排除该情形；P1 不能只比较 `steady_cpu_seconds` 而把搬出窗口的工作称为加速。

- [ ] **修正 / 通过条件：**在同一计时边界记录每流送入 / 接收 / 持久化计数、队列量和未完成工作，单列尾部补发 / 排空耗时；存在持续增长的积压或输入未按协议完成时，将该运行标为非稳态，不与已达稳态候选比较吞吐 / CPU。用一个故意落后并在尾部追赶的短负例验证分类即可，不新建容量测试框架。

## R3 · 中优先级：重用采样目录会先覆盖原日志

位置：[profile_steady.py](profile_steady.py#L68)，68–72 行；97–101 行和 129 行也使用固定输出名。

`steady_baseline.py` 虽会拒绝已存在的结果 JSON，父脚本却先以 `w` 打开原 `.stdout` / `.stderr`。因此按复测命令误用同一目录时，子程序拒绝启动之前，原测量日志已经被截断。父脚本失败后还没有本次 execution receipt，原 JSON 和原日志失去对应关系。

独立临时目录探针：预先写入结果 JSON 和两份内容为 `ORIGINAL_EVIDENCE` 的日志；模拟子程序按已有结果路径退出。父脚本报告 `steady start was not observed`，JSON 保留，两个旧日志均变为空字符串。探针不运行真实 profiler / Recorder。

- [ ] **修正 / 通过条件：**在打开任何输出和启动进程前一次性拒绝冲突，或每次使用独占新建的运行子目录；所有失败出口保留简短状态及已有文件。加入重复运行目录的短测试，要求旧结果、日志、栈和执行记录字节不变。无需扩展到新的证据管理系统。
