## P2-R4：REST 限流忽略服务器重试期限（高优先级，新增）

位置：`src/binance_market_data_recorder/collector/coverage.py:656–662`。
`poll_once` 将所有 429/418 都转换成固定 120 秒的共享池阻塞。上游的
`Retry-After` 已保存进响应证据，却没有参与调度。服务器要求等待 600 秒时，
其他请求会在 120 秒后获准重新发送；可能再次触发限流并延长整个 IP 的封禁。
要求短于 120 秒时也会产生不必要的停采。该问题同时影响 Spot 和共享 UM/CM 池。

离线复现走真实 `poll_once`、`capture_public_response`、RequestBudget 和 Raw
落盘，只替换网络客户端及预算时钟；临时目录由程序管理：

```bash
PYTHONPATH=. .venv/bin/python docs/milestones/P2/reproduce_rest_cooldown.py
```

| 输入 | 保存的 Retry-After | 预算实际等待 | 结果 |
| --- | ---: | ---: | --- |
| Spot / USD-M / COIN-M，各自 429 与 418，共 6 例 | 600 秒 | 全部 120 秒 | 全部失败；失败响应均已保留 |

复现退出码 1，见 [程序](reproduce_rest_cooldown.py) 和 [结果](review-cooldown.json)。
这不是计时误差或要求真实等待十分钟，预算时钟固定且直接读取下一次准入延迟。
官方 [Spot REST 说明](https://developers.binance.com/en/docs/products/spot/rest-api)
明确应遵守服务器等待秒数；现有 `spot/rate_limit.py` 已有秒数/日期/封禁截止时间
解析，`request_budget.py` 的 WS 拒绝处理也已复用它。

**修正要求：**复用已有重试边界语义，将实际剩余等待时间传给相应共享池；保留
原失败证据和停止取消行为。至少覆盖短/长 Retry-After、418 截止时间及既有缺省
处理；确认 UM 和 CM 共同受阻，Spot 独立。不需要新增限流框架或全量故障平台。

### R4剩余缺陷：冷却晚于失败记录落盘（高优先级）

位置：`collector/coverage.py:620`和`676–689`。`poll_once`已经拿到429/418
响应，但先`await persist_rest(result.envelope)`，在其返回后才调用共享预算的
`block`。真实落盘会等待spool锁和阻塞写入线程；这段时间其他源仍能拿到新的
准入并发请求。修正后的等待秒数正确，并不能弥补冷却启用之前的空窗。

新增[离线复现](reproduce_rest_cooldown_order.py)只替换网络客户端，并在真实
`persist_rest`入口设置可控等待；其后仍走原落盘和封存。先确定拒绝响应已经
返回，再启动不同源的新请求，不涉及已发出的在途请求：

| 收到拒绝的市场 | 后启动的新请求 | 输入 | 落盘等待期间预算延迟 | 新请求发出 |
| --- | --- | --- | ---: | --- |
| Spot | Spot另一源 | 429 / 418，各600秒 | 0秒 | 两例均是 |
| USD-M | COIN-M | 429 / 418，各600秒 | 0秒 | 两例均是 |
| COIN-M | USD-M | 429 / 418，各600秒 | 0秒 | 两例均是 |

全部六例失败，原失败响应均落盘；释放等待后才出现约600秒的正确冷却。
[结果](review-195762c-cooldown-order.json)保留每例的实际时长、请求与封存数量。
既有21项回归和[原六例](review-195762c-cooldown-duration.json)全部通过，因为
它们只检查`poll_once`完成之后的状态，未覆盖该异步等待边界。

**团队修正：**在拒绝响应返回后的首次异步等待之前，按既有解释启用相应共享池
冷却；随后照常保存失败证据，存储异常继续传播。保留UM/CM共享、Spot独立、
等待准入可取消和已发请求正常收尾。将上述六例变成短回归，并保留时长回归；
